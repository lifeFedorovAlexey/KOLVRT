Ты начинаешь новый проект операционной системы:

# KOLVRT
Kernel Outside Legacy, Versioned Routing & Translation

Это новый ARM64-first kernel на Rust.

KOLVRT НЕ является:
- переписыванием Linux на Rust;
- форком Linux;
- попыткой сохранить внутреннюю архитектуру Linux;
- попыткой обеспечить совместимость ценой загрязнения ядра.

Linux используется как крупнейшая база накопленного инженерного опыта: удачных решений, неудачных решений, исторических компромиссов, багов, regression policy, hardware quirks и последствий обратной совместимости.

Главная задача Phase 0 — НЕ писать ядро.

Сначала необходимо понять, какие проблемы накопились в Linux и других зрелых системах, почему они появились, какие из них действительно являются ошибками, какие — вынужденными компромиссами, и какие архитектурные правила KOLVRT должны предотвращать повторение этих проблем.

---

# 1. ОСНОВНАЯ ФИЛОСОФИЯ

Главный закон:

**The kernel must not adapt itself to legacy. Legacy compatibility must adapt itself to the kernel.**

Native kernel является источником истины.

Legacy compatibility никогда не должна определять внутреннюю архитектуру ядра.

Если старое приложение, драйвер или API требует исторически неправильного поведения:

ПЛОХО:

legacy component
    ↓
special-case inside kernel
    ↓
kernel forever carries legacy

ПРАВИЛЬНО:

legacy component
    ↓
versioned compatibility shim
    ↓
translation/routing
    ↓
clean native kernel

При этом рядом одновременно может существовать:

native component
    ↓
native API
    ↓
clean native kernel

---

# 2. COMPATIBILITY НЕ ЯВЛЯЕТСЯ ГЛОБАЛЬНЫМ РЕЖИМОМ

Категорически запрещено проектировать систему так:

system = native

или

system = compatibility

Разные компоненты должны одновременно использовать разные маршруты.

Пример:

Application A:
- memory -> native
- filesystem -> native
- networking -> native
- old synchronization API -> compat-v2

Application B:
- полностью native

Application C:
- Linux compatibility personality

Driver A:
- native

Driver B:
- compat-hardware-v3

Маршрутизация должна потенциально существовать на уровнях:

- executable/package;
- process;
- driver;
- device;
- subsystem;
- API family;
- protocol/version;
- конкретной compatibility capability.

Не усложняй routing без необходимости, но архитектура не должна предполагать один глобальный compatibility switch.

---

# 3. LEGACY QUARANTINE

Legacy-код не должен переноситься:

- в native driver;
- в native syscall implementation;
- в scheduler;
- в memory manager;
- в VFS core;
- в native ABI;
- в HAL только ради совместимости.

Историческая кривизна должна находиться в явно обозначенном compatibility module.

Compatibility module должен быть:

- отдельным;
- заменяемым;
- версионируемым;
- измеряемым;
- отключаемым;
- удаляемым;
- необязательным для native build.

Удаление compatibility module из build не должно ломать native path.

---

# 4. БАГИ САМОГО KOLVRT

Этот принцип распространяется и на будущие ошибки KOLVRT.

Если KOLVRT v3 имеет ошибочное поведение, а приложение начало от него зависеть:

НЕЛЬЗЯ сохранять ошибку в native kernel навсегда.

Необходимо:

1. определить root cause;
2. исправить native behavior;
3. написать regression test;
4. если реальная совместимость необходима — создать bug-compat module;
5. зарегистрировать старую семантику как versioned compatibility behavior;
6. измерять число зависимых consumers;
7. предоставить путь миграции;
8. удалить compatibility implementation, когда зависимостей больше нет.

Native specification всегда описывает правильное текущее поведение.

---

# 5. COMPATIBILITY DEBT ДОЛЖЕН БЫТЬ ВИДЕН

KOLVRT должен превращать legacy из невидимого архитектурного долга в измеримую характеристику.

Спроектировать возможность измерять минимум:

- native calls;
- compatibility calls;
- долю native execution;
- долю compatibility execution;
- активные compatibility modules;
- consumers каждого module;
- CPU time;
- wall latency;
- allocations;
- memory footprint;
- copies;
- context switches;
- lock contention;
- translations;
- serialization/deserialization;
- syscall/API frequency;
- throughput.

Не допускается искусственно замедлять compatibility path.

Если compatibility implementation быстрее native — система обязана показать это честно.

Это означает, что native implementation требует анализа и оптимизации.

---

# 6. A/B MIGRATION BENCHMARKS

Одной из главных особенностей KOLVRT должна стать возможность сравнить:

current compatibility path

с

target native path

на одном workload.

Разработчик должен видеть не лозунг "native лучше", а реальные числа.

Спроектировать benchmark methodology:

- identical workload;
- warm-up;
- достаточное количество iterations;
- median;
- p95;
- p99;
- variance/deviation;
- CPU;
- RAM;
- latency;
- throughput;
- allocations;
- context switches;
- copies;
- locks;
- архитектурные counters там, где доступны.

Никакого cherry-picking.

# 7. NATIVE / COMPAT SCORE

Diagnostic tooling должен показывать степень зависимости компонента от compatibility infrastructure.

Цветовая философия:

heavy legacy:
brown -> red

mixed:
yellow

native-oriented:
light green -> green

Цвет никогда не является единственным индикатором.

Обязательные текстовые состояния:

LEGACY
COMPAT
MIXED
MOSTLY_NATIVE
NATIVE

Score оценивает НЕ качество приложения.

Score означает только его зависимость от compatibility mechanisms.

Не придумывай произвольный маркетинговый score.

Исследуй, можно ли корректно выразить это одним числом.

Если нет — предложи multidimensional metrics вместо фиктивного числа.

# 8. SYSTEM PROFILES

Минимум два режима.

## DEV / DIAGNOSTIC

Предназначен для разработки и исследования.

Возможности:

- detailed tracing;
- live routing inspection;
- переключение native/compat, когда оно безопасно;
- A/B benchmark;
- invariant checks;
- assertions;
- compatibility dependency graph;
- counters;
- performance instrumentation;
- fault injection;
- debugging;
- verbose errors;
- safety diagnostics.

## PROD

Production execution.

Особенности:

- routing уже определён;
- compatibility modules заранее выбраны;
- ненужная diagnostics instrumentation отсутствует;
- live experimental switching отсутствует;
- минимальный overhead;
- никаких fake checks "на всякий случай";
- оптимизация execution path.

DEV и PROD используют одну архитектуру и одну codebase.

Нельзя иметь отдельный "настоящий prod kernel", архитектурно отличный от development kernel.

Разрешается compile-time elimination diagnostics.

Также проанализируй необходимость STAGING profile.

# 9. TARGET PLATFORM

Primary architecture:

AArch64 / ARM64.

Первичная среда разработки:

QEMU `virt`.

На начальном этапе ориентироваться на:

- AArch64;
- 64-bit only;
- EL1;
- MMU;
- GICv3;
- ARM Generic Timer;
- SMP;
- Device Tree;
- UART;
- VirtIO;
- PCIe там, где это разумно для дальнейшей архитектуры.

x86_64 может быть добавлен позже как Tier 2.

Core kernel не должен зависеть от AArch64 настолько, чтобы второй architecture port потребовал переписывания core subsystems.

---

# 10. IMPLEMENTATION LANGUAGE

Rust.

Основная часть kernel должна использовать safe Rust.

Unsafe допускается только там, где это объективно необходимо.

Для каждого unsafe участка обязательно:

- минимальный scope;
- SAFETY comment;
- documented invariant;
- причина невозможности safe implementation;
- тесты;
- reviewability.

Создай отдельную unsafe policy.

Запрещено использовать unsafe просто для удобства.

# 12. НЕ СЧИТАТЬ ВСЁ В LINUX ОШИБКОЙ

Для каждого case необходимо ответить:

1. Что реально произошло?
2. Когда решение появилось?
3. Почему оно было принято?
4. Какие ограничения существовали тогда?
5. Существуют ли они сегодня?
6. Это:
   - bug;
   - design flaw;
   - security issue;
   - hardware necessity;
   - performance tradeoff;
   - compatibility requirement;
   - deliberate architecture decision?
7. Какие последствия изменения поведения?
8. Как Linux решил проблему?
9. Почему решение нельзя/можно сделать лучше?
10. Как KOLVRT должен поступить?
11. Нужно ли поведение native kernel?
12. Нужно ли поведение compatibility layer?
13. Нужно ли оно вообще?

Нельзя делать выводы на основании только мнения автора статьи.

Предпочитать primary sources.
