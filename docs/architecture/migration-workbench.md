# Reproducible migration workbench

The [workbench](../../crates/migration-workbench/src/main.rs) executes a contained migration experiment on the available Windows host. It supplies actual process execution, contract checks, alternating A/B, local evidence signing and an isolated rollback check. It does not install software or mutate KOLVRT routes. Its workload is deliberately bounded; it is not a representative production application or a physical ARM64 kernel benchmark.

## Workload and execution

Current workload receipts use protocol `physical-host-process-library-v11` and encode
peak memory as a typed available/unavailable result. Contract-only execution records
`not_evaluated`; a platform without a collector records `unsupported_platform`; OS
measurement failures remain errors. A measured pair requires available peak-memory
measurements on both paths and rejects their absence. Historical receipts retain their
original encoding and do not establish execution of this protocol revision.

Two immutable, separately hashed fixture executables implement the same [window workload](../../crates/migration-workbench/src/lib.rs). Both reduce identical windows over an immutable 256-word dataset and check every sum and word count. The old client sends LE16 inclusive endpoints through the real versioned adapter; the candidate sends a native half-open Span through the real routing library. No artificial delays or different safety/resource rules favor either route.

Both executables run the routing conformance suite and the workload's empty/result checks. Measurements start after contract checks and warmup. Each warmup batch has 5000 operations; retain 3..20 batches and declare stabilization when the last three durations differ by no more than 20% of the minimum. Failed stabilization remains in the evidence and invalidates recommendation; it is never silently set to true. Each retained sample is one 50000-operation batch. The primary metric is whole-batch wall latency excluding process launch, contracts and warmup, including the same consumer/oracle work on both paths.

Before the paired measurement, the workbench launches a separate lifecycle worker against a dedicated state directory. The old process writes schema-v1 persistent state; a new process validates and writes schema v2 without deleting v1; another fresh process verifies the migrated data after restart. Keeping v1 available through candidate verification models the required staging boundary: retirement of the previous state is a later, separately authorized action. The workbench also retains the v1 snapshot, restores it after the candidate run and starts the old reader again, then compares restored bytes by SHA-256. Malformed state and an invalid state path must fail with retained diagnostics. The signed contract test references the exact worker executable digest, lifecycle receipt, snapshot and diagnostic artifacts, and a persistent-data proposal requires that receipt. These bounded fixture processes exercise persistence and rollback mechanics; they do not run inside an OS security sandbox or establish application permissions, real application lifecycle behavior, production restore safety or deployment authority.

The runner starts 100 fresh-process pairs in alternating A/B and B/A order. Fresh processes reset fixture state; there are no external or persistent writes in the workload. Independence is assumed for the exploratory bootstrap, not demonstrated merely by process creation. Background load, thermals, affinity and resource limits inherited from the host remain uncontrolled. All paired receipts, warmup, checksums, counters and durations are retained; outliers are not removed. A process/oracle failure or timeout aborts the experiment with retained failure evidence. Children have a ten-second deadline and bounded JSON receipts. This executor supports its trusted pure fixtures, not arbitrary untrusted applications or a general security sandbox.

Each measured process also retains a systematic request-latency sample every 241 calls. The host clock cannot resolve this fixture's individual calls reliably, so each observation times up to 16 consecutive calls and stores their mean nanoseconds per call. The latest run retained 20,800 group observations per path: baseline median/p95 10/10 ns and candidate 6/6 ns (p99 12/10 ns). These are descriptive group means, not individual-call tail guarantees or independent A/B observations; request groups do not change the 100 paired runs used for the main inference.

The predeclared statistical policy uses 100 pairs, 2000 bootstrap resamples, seed 7, nominal 95% confidence, a 1000-nanosecond gain margin and a 100000-nanosecond p95 latency regression budget. Each measured pair retains actual route-library copied-byte counters for all 50000 useful operations and the Windows process peak working set reported by `GetProcessMemoryInfo` since process launch. Both dimensions have a zero-byte p95 regression budget. The memory measurement includes startup, contract checks and warmup as well as the measured batch; it is a whole-process peak, not workload-only memory. Energy is unavailable and left unbudgeted; the report does not treat it as zero. p99 remains unavailable at this sample count. Windows host kernel bytes are captured for identity; source is `host_process`, which the advisor cannot promote to a verified KOLVRT OS migration.

## Provenance and rollback

Frozen executable bytes, data, specifications, suite, protocol, raw receipts and host kernel bytes enter a digest-addressed artifact store. An ephemeral Ed25519 key generated by OS randomness signs manifests, runtime assertions, contract results, benchmark payload and proposal. The private key is not saved; a separate `trust.json` exports only the experiment public key and signer roles. This is local reproducibility/provenance, not production signer provisioning or independent hardware attestation.

After A/B, the runner launches the retained old executable again, rechecks contracts and verifies the original data checksum and compat route. Executable bytes must remain unchanged through the experiment. This verifies rollback of the isolated next-process route choice for an immutable workload. It does not restore a running process, persistent database, installed package graph or external side effect. The proposal declares no persistent-data change and includes that exact rollback precondition.

`request.json` and `report.json` use the [advisor model](migration-advisor.md). Imported evidence is authenticated by the actual artifact-store verifier before the report is produced. The runner measures and retains 100 power-pilot pairs before the 100 measured pairs, signs the pilot as benchmark evidence, and binds a 90% prospective-power plan to its digest. The expected mean gain is declared as 25000 ns before both series (about 5% of the earlier fixture baseline); the pilot estimates variance only. This local scenario threshold is not an externally validated meaningful effect for KOLVRT. The advisor reports pilot variance, planned power and adequacy using a paired-block normal approximation. The latest retained run found a 209614 ns mean whole-batch gain, but rejected the candidate because the fixture consumer's p95 peak working set was 4096 bytes above baseline against its zero-byte budget. The same consumer's copied-byte budget passed. Its `consumer_id` is a signed local fixture label, not proof of installed-state or OS process ownership. Block length one remains an unvalidated independence assumption; the approximation does not establish independence or replace bootstrap assurance. The result is host-process evidence, not a production performance claim or deployment authorization.

## Commands and artifacts

Run from the repository root:

```text
cargo build --locked -p migration-workbench --release --bins
cargo run --locked -p migration-workbench --release -- run
cargo test --locked -p migration-workbench -p migration-advisor
cargo run --locked -p migration-advisor -- inspect-routing target/kernel/routing-results.json
```

The [earlier retained host result](../../research/results/migration-workbench.json) preserves the first 100-pair experiment. The [copied-byte result](../../research/results/migration-workbench-copied-bytes-1791037023253.json) retains the run with copied-byte gating. The [memory and copy result](../../research/results/migration-workbench-resources-1791038109618.json) retains an earlier run with process peak working set and copy receipts. The [first prospective-power result](../../research/results/migration-workbench-power-1791041621533.json) records its pilot and measured receipts. The [predeclared-effect result](../../research/results/migration-workbench-power-1791042671657.json) retains a run using a fixed 25000 ns expected gain declared before the pilot. The [consumer-budget result](../../research/results/migration-workbench-consumers-1791043885800.json) includes the fixture consumer ID and per-consumer resource assessment. The [request-latency result](../../research/results/migration-workbench-request-latency-1791047839386.json) preserves the latest 100-pair run and its sampled group-latency distributions. It measured baseline/candidate p95 working sets of 3973120 and 3977216 bytes against the zero-byte budget; per-consumer copied-byte p95 was 200000 and 0, so that budget passed. The mean whole-batch latency gain was 209614 ns. These observations apply only to this host fixture. The bundled JSON keeps the request, report, raw receipts and descriptive statistics; the local experiment directory additionally retains executable and binary artifacts.

Every workbench experiment creates `target/migration-workbench/<epoch-millis>-<pid>/` with frozen fixture executables, contract/paired/rollback receipts, the artifact store, request, external trust policy, report and descriptive statistics. Existing runs are preserved. Raw output includes failed attempts; a later run does not overwrite them. This initial runner requires the Windows host kernel file and fixtures built alongside the runner. No paid server, hardware rental or external credentials are needed.

The [OS evidence bridge](../../crates/migration-advisor/src/routing_evidence.rs) reads saved `cargo xtask routing test` output. It emits schema v6 and reads v4/v5 for compatibility. The v4 `adapter_cpu_*` fields and v4/v5 `exclusive_cpu_ns` summary are normalized only as historical route-EL0 and combined measured-segment observations; they do not establish adapter-only CPU cost. In v6 the aggregate is named `measured_segments_cpu_ns`: it sums the separately sampled route-EL0 interval and native service body. Kernel completion records carry the actual ProcessId slot/generation, fixed CPU owner and owned resident frame count. The exporter joins each identity to the exact loaded image digest and EL0 route-generation report. It verifies raw chunk offsets/completions, terminal success, kernel/package identities, report headers and accounting, and cross-checks summaries/samples against raw words. It preserves warmup and preemptions, converts median timer ticks with the declared frequency, and reports EL0 route-call residency separately from native service time; the EL0 interval includes client/wrapper code and exception-boundary overhead, so it does not isolate adapter-only CPU time. These QEMU fixtures do not establish a package manager's installed-state identity or physical host telemetry. Producer assertions remain unsigned. Sequential samples within one QEMU run are never converted into independent paired runs or a preferred migration. Stripped PROD reports have declarations and contract results without invented dynamic shares.

[Workload/process checks](../../crates/migration-workbench/tests/workload.rs) exercise actual path equivalence, distinct compat/copy counts, executable contract checks and process failure propagation. [Bridge checks](../../crates/migration-advisor/tests/routing_evidence.rs) reject corrupt summaries/raw data, failed or missing completions, lost chunks and mismatched kernel identity.

## Integration boundary

The host experiment and the QEMU bridge export distinct, bounded scopes. Production still needs actual installed-state/catalog ownership, isolated real application contracts, persistent-data restoration drills, trusted signer provisioning/freshness, workload dependence/environment control, exclusive adapter/native CPU accounting and a physical ARM64 KOLVRT runner. The same evidence model supports those producers; their results must retain their actual scope. The parent migration issue stays open until its remaining acceptance criteria are met.
