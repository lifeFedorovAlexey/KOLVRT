# Документация и переводы

## Статус и свидетельства

В документах, этапы которых можно перепутать, указывать `Document status`, `Evidence scope`
и локальную ссылку `Current reference`. Если документ заменяет другое решение полностью
или частично, добавлять поле `Supersedes`. Эти поля не связаны со стадиями публикации ABI. Допускаются только эти имена полей; устаревшие имена отклоняются даже вместе с новыми полями.

| Статус               | Значение                                                                                      |
| -------------------- | --------------------------------------------------------------------------------------------- |
| CURRENT              | Действующая политика или описание реализации в указанных пределах свидетельств.               |
| DESIGN BASELINE      | Принятое требуемое поведение с явными пробелами реализации и приёмки.                         |
| HISTORICAL           | Заявления об именованной прежней фазе или редакции, а не текущей реализации.                  |
| HISTORICAL MILESTONE | Свидетельства и утверждения в границах завершённого этапа; поздняя работа их не переписывает. |
| SUPERSEDED           | Заменён для указанной области; сослаться на замену и сохранить незатронутые обязательства.    |

Код устанавливает реализованное поведение; действующие принятые ADR и спецификации задают
требуемое поведение. Расхождение — дефект либо требует рассмотренного решения, а не
автоматического правила CODE > ADR > DOC. Исторические заявления не отменяют текущие решения.
Замена может быть частичной: планировщик не завершает IPC, дескрипторы или отмену.

## Рассмотренная проверка статуса

Задача #6 проверяет слитую реализацию по `d6bf7da`, исключая локальные изменения Phase 2.
[ADR-0010](architecture-decisions/0010-kernel-foundation.md) фиксирует исходное выполнение
только CPU0; [ADR-0012](architecture-decisions/0012-multicore-retirement.md) и
[ADR-0014](architecture-decisions/0014-el0-foundation.md) фиксируют последующие ограниченные этапы.

| Утверждение или документ        | Решение                                                                                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ядра или его сборки нет         | Только историческая Phase 0; слитый репозиторий содержит собственное ядро AArch64.                                                                   |
| Проверки ядра не выполнялись    | Только историческая Phase 0; сохранённые результаты основы, SMP и EL0 в QEMU существуют.                                                             |
| Выполнение только CPU0          | Область исходной Phase 1; владение распределителем у CPU0 — отдельное действующее ограничение.                                                       |
| Первый собственный сценарий     | DESIGN BASELINE; ограниченные этапы EL0, планировщика и маршрутизации реализованы, приёмка IPC, дескрипторов, отмены и служб остаётся незавершённой. |
| Политики совместимости и unsafe | Действующие обязательства CURRENT с историческими фрагментами Phase 0; общий загрузчик или полное доказательство безопасности не заявлены.           |
| Локальная маршрутизация Phase 2 | Незакоммиченные код и результаты не являются слитой реализацией или свидетельствами рассмотренной редакции.                                          |

Сохранённые [результаты основы](../../../research/results/kernel-foundation.json) охватывают
23 теста на профиль и один активный CPU; [результаты SMP](../../../research/results/kernel-smp.json)
охватывают 39 тестов и два активных CPU на записанной редакции `a9371e7`;
[результаты EL0](../../../research/results/kernel-el0.json) охватывают 53 теста на записанной
редакции `67e4cbc`. Эти записи DEV/PROD используют QEMU 10.1.0, cortex-a57, TCG, 256 MiB
и два настроенных CPU. Идентичности исходников и артефактов и отрицательные проверки относятся
к каждой записи, а не автоматически к текущему коду. Физический ARM64, SMP общего назначения
и полный собственный сценарий остаются непроверенными. Это изменение не перезапускает матрицу
ядра и не создаёт новых свидетельств выполнения.

Ограниченные проверки проверяют метаданные и локальные ссылки во всех документах, где они
указаны. Проверка переводов сопоставляет статус ADR, сведения о замене и цели ссылок на разных
языках. Она не подтверждает смысловую эквивалентность описания области свидетельств или
соответствие заявлений реальному поведению. Сверять каждое заявление о возможностях с конкретной
редакцией кода, профилем и платформой.

Основные документы Markdown пишутся полностью на английском. Переводы находятся в `translations/<language>/` и повторяют пути основных документов в репозитории, включая имена файлов. Для русского используется `translations/ru/`. Использовать описательные имена каталогов, например `architecture-decisions`; избегать необъяснённых сокращений в новых именах каталогов.

Переводить весь смысл: требования, исключения, неопределённость, примеры и выводы. Не смешивать английскую и русскую прозу. Сохранять код, команды, идентификаторы, имена собственные и внешние адреса там, где перевод изменил бы их смысл. Русские навигационные ссылки остаются внутри русского дерева; ссылки на общие данные и исходный код ведут к основным файлам.

Каждый основной документ Markdown требует соответствующего перевода для каждого зарегистрированного языка. Сохранять одинаковую иерархию заголовков, списки, форму таблиц, порядок целей ссылок и идентификаторы законов. Оба документа ссылаются друг на друга. Новые языки регистрируются в `translations/manifest.json` и предоставляют полное зеркальное дерево.

Реестр записывает контрольные суммы SHA-256 обоих проверенных текстов с приведением CRLF к LF. Изменение любого текста делает запись пары устаревшей. Проверки никогда не обновляют суммы незаметно. После проверки полной пары выполнить явную команду записи, описанную в [руководстве инструментария](../crates/repository-checks/README.md). Проверки структуры и редакций выявляют рассогласование, но не доказывают языковую эквивалентность. Проверка человеком остаётся обязательной.

Исходное задание сохранено историческим текстовым вложением. Исследовательские JSON сохраняют первоначальный текст анализа источников; это не переводы Markdown. Двуязычный каталог указателя случаев содержит проверенные английские и русские названия, обозначения подсистем и вопросы, связанные с контрольной суммой исследовательской записи. Изменение записи требует проверки этого каталога до повторного формирования указателей.

## Обновление доказательств Phase 2

Прежняя проверка явно исключает тогдашнюю локальную работу Phase 2. Проверенный [контракт маршрутизации](kernel/routing.md) и [ADR-0015](architecture-decisions/0015-el0-versioned-routing.md) описывают ограниченный сценарий в необязательном образе EL0: восемь независимых потребителей на двух CPU, маршруты native/v1/v2/safe-bug, закреплённые профили PROD и изоляцию от набора зависимостей native-ядра. [Результаты выполнения](../../../research/results/routing-phase2.json) и [свидетельства физического удаления исходников](../../../research/results/native-compat-removal.json) сохраняют точные границы исходников и артефактов; в последней проверке повторно пройдена та же основа DEV/PROD с 53 тестами и одиннадцатью отрицательными проверками без пакетов маршрутизации. Эти записи подтверждают только результаты в QEMU. IPC, передача полномочий, отмена, общие службы, динамическая загрузка и проверка на микросхемах остаются незавершёнными; полный первый собственный сценарий по-прежнему является проектной основой.

## Обновление evidence Phase 3.0

[Владение планировщиком](kernel/scheduler.md) и [ADR-0016](architecture-decisions/0016-scheduler-ownership.md) заменяют прежнюю модель доступа во время выполнения, которая опиралась только на комментарии, и сохраняют свидетельства прошлых этапов. [Результаты Phase 3.0](../../../research/results/kernel-phase3.json) содержат 54 теста для каждого профиля, обе загрузки без тестового режима и 41 отрицательную проверку; [результаты регрессии маршрутизации](../../../research/results/routing-phase3-regression.json) сохраняют поведение с необязательной нагрузкой. Phase 3.0 не завершает динамический жизненный цикл процессов, безопасное копирование из пользовательской памяти, полномочия и домены безопасности, IPC, надзор или постоянные службы. Для этих этапов нужны отдельные разрешения и свидетельства.

## Обновление свидетельств Phase 3.1

[Динамические процессы](kernel/processes.md) и [ADR-0017](architecture-decisions/0017-process-lifecycle.md) описывают завершённый ограниченный внутренний этап. [Результаты ядра](../../../research/results/kernel-phase31.json) сохраняют 65 тестов для каждого профиля DEV/PROD и 53 отрицательные проверки, включая прежние 54 теста и 41 проверку. Stress выполняет 32 раунда на двух CPU, то есть 64 цикла жизненного цикла на профиль, с повторным использованием поколений, локализацией отказов и восстановлением числа ресурсов. [Регрессия маршрутизации](../../../research/results/routing-phase31-regression.json) и [физическое удаление compatibility](../../../research/results/native-compat-removal-phase31.json) сохраняют точные границы выполнения. Публичные полномочия на создание и ожидание из EL0, постоянные службы, асинхронное освобождение ресурсов и безопасное копирование пользовательской памяти отложены. Эти свидетельства подтверждают ограниченное поведение в QEMU, а не проверку на микросхемах или завершение полного собственного сценария.
