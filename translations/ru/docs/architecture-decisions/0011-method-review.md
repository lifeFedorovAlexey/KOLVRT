# ADR-0011 — Ревью методов по производительности и надёжности

Статус: **Принято**. Дата: 2026-10-02.

Document status: HISTORICAL MILESTONE
Evidence scope: состояние создания маршрутов совместимости на момент принятия ADR; позднее маршрутизация совместимости была принята в Phase 2.
Current reference: [Версионированная маршрутизация EL0](0015-el0-versioned-routing.md)

## Context

Пользователь требует performance-first выбора методов с балансом надёжности и проверкой исторических ошибок ОС до принятия. Одни benchmarks этого требования не обеспечивают.

## Decision

Требовать [правило принятия реализации](../architecture/implementation-review.md) до принятия методов. Проверять альтернативы, затраты, зависимости отказов и соответствующие случаи до принятия реализации. Предпочитать самый быстрый проверенный вариант в рамках ограничений корректности; отделять аргументы сложности от измеренного сравнительного превосходства. Это реализует LAW-040, LAW-036 и LAW-041 без закона ради квоты.

## Alternatives

Выбирать по привычке, копировать механизм известной ОС, оптимизировать только happy paths либо откладывать исправления корректности как временную архитектуру.

## Why rejected

Популярность не доказывает соответствие нагрузке. Известные механизмы отказа остаются ошибками, даже если копируемый код быстрый. Неизмеренное ранжирование не удовлетворяет честному наблюдению.

## Consequences

Каждое существенное изменение требует проверяемого выбора, инвариантов, ограниченного поведения отказа и свидетельств. Нарушение закона останавливает решение и требует альтернативы через ADR. Недоступные сравнительные данные фиксируются, а не выдумываются.

## Compatibility impact

Такое же ревью позже применяется к compatibility routes; сейчас они не создаются.

## Performance impact

Проверять число hot-path операций, memory traffic, metadata, contention, tail latency и стоимость DEV в PROD. Измерения требуют нагрузки, единиц, прогрева, итераций и raw samples. Наблюдения TCG не доказывают аппаратный throughput.

## Security impact

Authority, initialization, alias lifetime, memory ordering и failure containment — ограничения принятия, а не регулируемые shortcuts для benchmark.

## Testing

Настоящие subsystem tests, negative controls и проверка реализации дополняют измерения. Host-only models не заменяют kernel faults и IRQ validation. Unsafe inventory не заменяет ревью инвариантов.

## Reversibility

Пересматривать выбор при изменении нагрузки или платформы; сохранять свидетельства и сравнивать замену. Не расширять автоматически scheduler, userspace и compatibility.
