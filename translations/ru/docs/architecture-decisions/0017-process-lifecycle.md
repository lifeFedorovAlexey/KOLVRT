# ADR-0017 — Жизненный цикл собственных процессов с защитой от устаревших поколений

Status: **Принято для ограниченного Phase 3.1**. Дата: 2026-10-03.

Document status: HISTORICAL MILESTONE
Evidence scope: принятое ограниченное решение Phase 3.1 для доверенных загрузочных задач на двух CPU; публичного API жизненного цикла для EL0 нет.
Current reference: [Контракт жизненного цикла процессов](../../../../docs/kernel/processes.md)

## Контекст

Теперь планировщик владеет очередями исполнения для каждого CPU, но жизненному циклу процесса также нужны стабильная идентичность, удержание владельца адресного пространства, транзакционное создание, фиксация конечного результата и безопасное освобождение ресурсов. Повторное использование слота или освобождение кадров до отсоединения всех ссылок планировщика может привести к тому, что устаревшая ссылка начнёт обращаться к другому процессу. Более широкая тема собственного жизненного цикла процессов и служб описана в issue #20.

Текущая реализация — доверенный загрузочный механизм для ограниченных задач. Это ещё не общий диспетчер служб и не пользовательский API управления процессами.

## Решение

Принять текущий протокол Phase 3.1 как ограниченный внутренний этап ядра:

- Идентифицировать процесс закрытыми номером слота и проверяемым ненулевым поколением `u64`. Не допускать переполнения и отката уже израсходованного поколения, в том числе при неудачном создании.
- Использовать единственный закрытый `Registry`, создаваемый при запуске ядра и сохраняемый между нагрузками. Постоянная отметка о создании экземпляра не позволяет другому реестру сбросить поколения идентификаторов.
- На этом этапе использовать четыре слота планировщика на CPU и фиксированное закрепление задач за CPU. Создавать процессы может только доверенный загрузочный код; запрос создания с явным источником `Origin::El0` отклоняется до резервирования.
- Создавать ресурсы транзакционно. Не публиковать исполняемую задачу, пока адресное пространство и начальный контекст не подготовлены полностью. При сбое освобождать все ресурсы, сохраняя израсходованную идентичность недействительной.
- Различать состояния `Prepared` и `Admitted`. Операция `start` допускает подготовленный процесс к исполнению; `dispatch` публикует дескрипторы только после полной подготовки и направляет их соответствующему CPU.
- Фиксировать штатное завершение, перехваченный отказ, явно заданный предел времени задачи или ошибку создания во внутренней записи ядра. Это не определяет публичные блокирующий вызов или API ожидания.
- Освобождать ресурсы, только когда процесс с точным поколением завершён, оба CPU подтвердили завершение исполнения, корни планировщика отсоединены под исключительным разрешением на безопасное изменение и больше нет владельца, который мог бы исполнять задачу. Тайм-аут не разрешает освобождение.
- Сохранять консервативный барьер для двух CPU. Не допускать следующий цикл и не освобождать один процесс, пока процесс на другом CPU из текущего цикла ещё может исполняться.
- Не связывать идентификатор процесса с полномочиями. Решение не добавляет IPC, дескрипторы, capabilities, домены безопасности, загрузчик ELF, миграцию задач, публичные API создания и ожидания или общую политику допуска постоянных служб.

Issue #20 остаётся открытым: предстоит определить публичные полномочия управления жизненным циклом, асинхронный поиск и ожидание завершения, а также политику допуска служб. Для ослабления барьера потребуется отдельно проверить протокол удержания ссылок и безопасного изменения каждого объекта.

Сохраняются обязательства LAW-013, LAW-018, LAW-035, LAW-041 и LAW-043. Новый закон или исключение по привилегиям не добавляется. Координатор процессов учитывает владение вокруг уже существующих публикации защищённых таблиц страниц, привилегированного переключения контекста и освобождения после покоя. Это не новая ответственность за политику служб: будущий надзорный процесс EL0 сможет выбирать политику жизненного цикла, но не сможет сам публиковать защищённые таблицы, активировать TTBR или выполнять привилегированную TLBI. В этом ограниченном фундаменте у EL0 ещё нет авторизованной точки создания процессов. Узкие механизмы остаются в EL1, а публичная политика отложена до появления контрактов копирования памяти и полномочий. Перед допуском вызывающих служб владельцы подсистем памяти и планировщика должны пересмотреть размещение; стратегия выделения и надзор над службами находятся вне этого механизма. Его TCB остаётся владельцем кадров, записью отображений, архитектурным переключением и протоколом владения планировщиком.

## Альтернативы

- Повторно использовать слоты процессов без поколений.
- Уже сейчас открыть внутренний реестр через API создания и ожидания из EL0.
- Освобождать каждый процесс сразу после его завершения, независимо от других CPU.
- Включить в этот этап общий асинхронный диспетчер служб.

## Почему альтернативы отклонены

Без поколений невозможно распознать устаревшую идентичность после повторного использования слота. Открытие создания до определения полномочий и правил безопасного копирования из памяти пользователя создаст впечатление, будто числовой идентификатор или адрес сами дают доступ. Отдельное освобождение ресурсов небезопасно, пока каждый CPU не отпустил корни планировщика и владение исполнением. Общий диспетчер служб выходит за рамки текущей реализации и подтверждающих её данных.

## Последствия

Загрузочные задачи получают стабильные идентификаторы, создание с безопасным откатом, записи о завершении, ограниченную вместимость и проверяемое освобождение ресурсов. Барьер для двух CPU ограничивает параллелизм и увеличивает задержку освобождения. Реестр и адресные пространства остаются закрытыми от пользовательского кода. Issue #20 не завершён.

## Влияние на совместимость

Решение расширяет собственный загрузочный путь и не меняет маршрутизацию наследуемой совместимости, а также не предоставляет ей полномочий на управление процессами. Неподдерживаемая попытка создания из EL0 вызывает отказ только в вызывающем процессе. Существующие загрузочные тестовые задачи используют тот же внутренний путь create/start/dispatch/reclaim.

## Влияние на производительность

Создание использует ограниченный непрерывный диапазон кадров и не требует потенциально аварийного расширения кучи. Фиксированная вместимость и синхронный барьер для двух CPU ограничивают пропускную способность. Без отдельных измерений улучшение производительности не заявляется.

## Влияние на безопасность

Поколения позволяют отклонять устаревшие ссылки; закрытое владение удерживает ресурсы адресного пространства; откат не допускает частичной публикации; отказ задачи изолируется; кадры освобождаются только после безопасного отсоединения ссылок. Идентификаторы процессов и числовые адреса сами по себе не дают полномочий. Этот этап не обеспечивает безопасное копирование из памяти пользователя, IPC, дескрипторы, capabilities или домены безопасности.

## Проверки

Матрица QEMU для Phase 3.1 проверяет профили DEV и PROD на двух CPU, включая границы создания и отката, допуск, штатное завершение и отказы, исчерпание вместимости, устаревшие поколения, повторные операции, разреженные очереди и возврат физической памяти. Записанные данные проверки указаны в [контракте жизненного цикла](../../../../docs/kernel/processes.md). Это ограниченный детерминированный прогон, а не подтверждение длительной надёжности, fuzz-тестирования или слабой модели памяти на реальном оборудовании.

## Обратимость

Внутренний протокол можно пересмотреть до появления публичных зависимых от него клиентов. После появления внешних API или постоянных служб изменения потребуют явного плана совместимости.
