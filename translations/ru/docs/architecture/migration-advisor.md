# Советник миграции на основе capabilities

В KOLVRT есть отдельная подсистема хоста только для чтения, которая превращает долг совместимости в предложение миграции. [Реализация](../../../../crates/migration-advisor/src/lib.rs) использует схему v3 — развивающийся интерфейс планирования, а не замороженный ABI проекта. Более ранние версии запросов явно отклоняются. Ограниченный QEMU exporter реализован; production-сбор ядра и интеграция с пакетным менеджером не реализованы.

```text
runtime evidence -> required capabilities -> dependency solutions
                 -> exact-artifact contract tests -> paired A/B evidence
                 -> migration proposal with rollback -> authorized deployment
```

## Анализ и размещение

[Debian Provides](https://www.debian.org/doc/debian-policy/ch-relationships.html#virtual-packages-provides), [виртуальные зависимости Spack](https://spack.readthedocs.io/en/latest/packaging_guide_creation.html#virtual-dependencies) и [CUDF/Mancoosi](https://www.mancoosi.org/cudf/) обосновывают зависимости от интерфейсов и решатель, отделённый от исполнения пакетного менеджера. Это архитектурные ориентиры, а не заявления о совместимости форматов. Разрешимый граф не доказывает поведение, совместимость данных, гарантии сохранности, права, корректность запуска или производительность.

Пакетные capabilities описывают возможности, а не полномочия безопасности ядра. Импорт каталога, решение, исполнение контрактов, измерения, рекомендации и развёртывание разделены и находятся вне EL1. Похожие имена, описания или эмбеддинги не удовлетворяют требованию. Обязательные пути остаются требованиями, даже когда телеметрия никогда их не наблюдает.

Правило подсистемы: **Наблюдение может рекомендовать. Развёртывание требует отдельного полномочия.** Оно определяет границу советника, а не новый нумерованный закон ядра. Изменение набора законов ядра требует процесса архитектурных решений. У советника нет API установки или изменения маршрутизации; `automatic_replacement` и `deployment_authorized` каждого предложения всегда равны false.

## Версионируемые семантические контракты

[Модель](../../../../crates/migration-advisor/src/lib.rs) разделяет `capability_id`, `semantic_version` (`major`, `minor`, `patch`) и `contract_digest`. Digest идентифицирует точные байты спецификации; он не является идентичностью совместимости. Зависимости сопоставляются по ID возможности и включительному интервалу семантических версий внутри одной положительной основной версии. Нестабильные контракты с нулевой основной версией и интервалы через основные версии в этом профиле не поддерживаются. Объявленные совместимые расширения minor/patch могут иметь разные digest. Семантическая совместимость остаётся явным заявлением, а не фактом, выведенным только из номера версии.

Требование сохраняет digest спецификации потребителя для тестирования. Кандидат должен пройти как собственную объявленную спецификацию, так и требуемую спецификацию потребителя. Успех только новой спецификации поставщика не доказывает старое поведение потребителя. Несовместимая основная версия требует явной миграции потребителя, а не упрощённого сопоставления. Версии выпусков пакетов остаются отдельными положительными целыми числами в первоначальном формате каталога.

Требования — списки AND из альтернатив OR. Пакеты объявляют `provides`, `requires`, `conflicts`, имя, версию выпуска и digest артефакта. Повторные/неоднозначные манифесты и пустые альтернативы отклоняются. Запрос задаёт фактическое установленное замыкание, поверхность замены и требования сохраняемых потребителей. Корневой кандидат сам должен предоставлять поверхность замены. Редкие пути запуска, форматы состояния и обязательства жизненного цикла включаются явно; runtime не может их стереть.

## Профиль решателя и проверка

[Решатель и проверяющий компонент](../../../../crates/migration-advisor/src/solver.rs) независимы от развёртывания. CLI выполняет ограниченный поиск замыканий зависимостей в каталогах до 256 пакетов. Он ветвится по неудовлетворённому требованию с наименьшим числом доступных поставщиков, запоминает выбранные замыкания и сравнивает полные альтернативы по числу пакетов, затем по отсортированной идентичности артефактов. CLI ограничивает кандидата 524288 различными замыканиями; исчерпание бюджета отличается от UNSAT. Для небольших каталогов до 20 пакетов доступен независимый эталонный полный перебор. Циклы разрешены при удовлетворённых требованиях. Проверяющий компонент независимо проверяет идентичности, транзитивное замыкание, сохраняемые требования и конфликты, а также фактический установленный исходный план, не создавая вымышленный.

`reference_single_version` указывается как модель разрешения зависимостей. Ограничение одной версии на имя пакета относится к этому первому профилю решателя/проверяющего компонента, **а не к архитектуре KOLVRT**. Параллельные runtime, варианты ABI, старые замыкания приложений и пространства имён sandbox требуют явной модели областей и проверяющего компонента. Будущий пакетный менеджер не должен запрещать их только потому, что эта эталонная реализация их не охватывает. Ограниченный решатель исследует альтернативные планы зависимостей в рамках одной версии; масштабируемый scoped solver и интеграция SAT/CUDF остаются открытой работой.

## Уровни свидетельств и предложения

[Советник](../../../../crates/migration-advisor/src/advisor.rs) записывает контекст: идентичность машины, digest нагрузки/ядра/протокола и источник (`os_runtime`, `host_model` или `host_process`). Записи runtime связывают идентичность пакета, окно, поколения маршрутов, digest адаптеров, допуски native/compat, ошибки, исключительное процессорное время адаптера в наносекундах и скопированные байты. Отсутствующая стоимость остаётся неизвестной. Известные дорогие маршруты и маршруты с неизвестной стоимостью разделены. Доля совместимости неизвестна при потерях событий, неполной классификации или отсутствии допусков; наблюдения никогда не доказывают возможность удаления модуля. Следуйте [диагностическому контракту](diagnostics.md).

У результатов есть явные измерения подтверждённости и недостающие проверки, а не вымышленная численная оценка уверенности:

- `VERIFIED_CANDIDATE`: решение зависимостей, тесты контрактов поставщика/потребителя, аутентифицированные свидетельства, полное наблюдение compat в ОС без потерь, статистически поддержанное улучшение и документированный откат удовлетворяют проверкам этого профиля.
- `PARTIAL_EVIDENCE_CANDIDATE`: решение зависимостей существует, но некоторые проверки отсутствуют, недостаточны, не подписаны или неполны. Показываются доступные тесты, измерения, откат и точные пробелы. Потерянная телеметрия запрещает сильное предпочтение, а не поиск или представление.
- `REJECTED_CANDIDATE`: переданная проверка контракта/результата/действительности эксперимента провалилась либо измеренная регрессия хвоста превысила бюджет. Отсутствующие свидетельства не являются проваленным тестом.
- `BLOCKED`: решение некорректно, неразрешимо или исчерпало бюджет; указывается отдельная причина.

Каждый кандидат с решением включает предложение с `candidate`, `expected_gain`, `required_changes`, `rollback_strategy`, `rollback_preconditions` и `irreversible_changes`. Непереданные поля явно равны null, а не считаются безопасными. Метаданные плана миграции связывают план кандидата и контекст эксперимента и требуют собственной доверенной подписи для проверенного статуса. Выигрыш и доверительный интервал вычисляются из аутентифицированных выборок, а не принимаются как заявленные сводки.

Откат поддерживает восстановление снимка, связанного с digest, переустановку точного предыдущего плана или явное объявление недоступности отката. Переустановка отклоняется как откат при изменениях постоянных данных. Устаревший исходный план, отсутствующий откат или объявленные необратимые эффекты сохраняют частичный статус кандидата. Digest снимка и подписанный план аутентифицируют документированную стратегию; они не доказывают успешную проверку восстановления и не восстанавливают внешние побочные эффекты. Развёртывание должно отдельно проверить предусловия отката, испытать восстановление и предоставить полномочия на необратимые изменения.

## Статистическая политика A/B

[Статистический модуль](../../../../crates/migration-advisor/src/statistics.rs) заменяет требование выигрыша каждой пары интервалом парного процентильного bootstrap для **среднего абсолютного выигрыша задержки по настенным часам**. Пересэмплирование работает с упорядоченными парами целых прогонов; запросы внутри одного прогона не являются независимыми наблюдениями. Заранее заданный `resampling_block_length` выбирает циклическое блочное пересэмплирование: длина 1 соответствует обычному bootstrap с предположением независимости. Одна шумная пара сохраняется и может быть допустима. Выбросы не удаляются. Seed, минимум эффективной выборки, длина блока, уровень доверия, число повторов bootstrap, минимальный полезный выигрыш и бюджеты регрессии p95/p99 объявляются заранее и включаются в подписанный результат бенчмарка; изменение политики нарушает сопоставимость.

Политика принимает 30..4096 блоков пересэмплирования, 2000..10000 повторов bootstrap и 90%..99% номинального доверия. Пример использует 100 блоков, 2000 повторов и 95%. Для длины блока L требуется не менее `min_resampling_blocks * L` упорядоченных прогонов; доступность хвостов определяется `floor(число_прогонов/L)` блоками. Число блоков не доказывает независимость и не гарантирует достаточную мощность или покрытие. Проверка требует нижнюю границу интервала выше объявленного порога выигрыша и регрессию p95 в пределах бюджета. Необязательный бюджет p99 требует доступных свидетельств p99. Указываются абсолютный эффект, относительный средний эффект, интервал, медиана, p95 и p99. Квантили по ближайшему рангу используют `sorted[ceil(p*n)-1]`. p95 остаётся недоступным ниже 100 блоков, p99 — ниже 1000; это консервативные ограничения доступности, а не универсальные гарантии точности хвоста. Они описывают **длительность нагрузки на уровне прогона**, а не задержку объединённых запросов.

Необязательные `p95_memory_regression_budget_bytes`, `p95_copied_bytes_regression_budget` и `p95_energy_regression_budget_uj` ограничивают регрессию p95 для пикового resident memory в байтах, объёма копирования потребителем в байтах и энергии в микроджоулях соответственно. Парные значения baseline/candidate должны присутствовать для каждого сохранённого прогона. Если объявленный бюджет не обеспечен полными измерениями или 100 эффективными блоками, результат получает `insufficient_resource_evidence` и не подтверждает выигрыш; превышение p95 бюджета даёт `resource_regression`. Это независимые пределы по измерениям, а не единый показатель полезности. Host workbench сохраняет скопированные байты и пиковый working set всего процесса в Windows с нулевыми бюджетами регрессии p95; энергия пока не измеряется и не ограничивается. Результат этой тестовой нагрузки не подтверждает production телеметрию ресурсов.

Корни кандидатов из переданного каталога, удовлетворяющие поверхности замены, образуют семейство сравнений. Для каждого benchmark интервал доверия корректируется методом Бонферрони на размер семейства, включая корни без подходящего бенчмарка. В отчёте указаны размер семейства, скорректированный уровень доверия и число выборок в хвостах. Если число повторов даёт менее 20 выборок хотя бы в одном скорректированном хвосте, результат получает статус `inadequate_comparison_resolution` и не может подтвердить выигрыш. Так отсутствие бенчмарка не уменьшает семейство после обнаружения кандидатов. Это не доказывает полноту каталога реальных альтернатив; минимальное число выборок в хвосте также не является расчётом мощности.

Bootstrap предполагает репрезентативность парных прогонов и даёт приближённое покрытие. Длину блока нужно выбирать по пилотному прогону или иному заранее заданному анализу зависимости; советник не выводит статистически оптимальную длину и не доказывает полноту сохранённой производителем последовательности. Включённый host workbench использует длину 1, поэтому его предположение о независимости остаётся непроверенным. Блочное пересэмплирование не исправляет цензурирование и не заменяет перспективный анализ мощности. Следуйте [методологии бенчмарков](benchmarking.md): эквивалентные полезные результаты, одинаковая безопасность и квоты, сброс данных эксперимента, независимые снимки для побочных эффектов, сохранение прогрева/сырых выборок и заранее объявленные правила остановки/исключения.

Советник также проверяет чередование порядка A/B, постоянное число полезных единиц, успешные проверки результата/стабилизации и отсутствие ошибок/тайм-аутов/незавершённых запросов. Суммарные измеренные допуски совместимости должны снижаться; отдельные шумные пары не обязаны все улучшаться. Метка native не даёт бонуса. Неудачные или неполные измерения нельзя скрыть быстрой медианой.

`preferred_observed` выбирает минимальную наблюдаемую медиану среди проверенных кандидатов с одинаковыми полезными единицами; равные медианы или разная работа не дают предпочтения. Это наблюдаемый порядок, а не доказательство статистического превосходства между всеми кандидатами. Автоматический выбор длины блока, перспективный анализ мощности, совместный анализ компромиссов между ресурсами и измерения каждого альтернативного замыкания остаются будущей работой.

## Происхождение свидетельств и граница доверия

[Модуль provenance](../../../../crates/migration-advisor/src/provenance.rs) реализует проверку Ed25519 с закреплённой `ed25519-dalek` и её [API строгой проверки](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict). Политика доверия и корень артефактов передаются отдельно от запроса. Вход не может установить собственный доверенный ключ или заявить `verified: true`. Без внешнего проверяющего компонента CLI никогда не присваивает проверенный статус, даже если все импортированные флаги `passed` истинны.

У доверенных ключей есть явные роли (`catalog`, `runtime`, `contract_test`, `benchmark`, `proposal`) и флаги отзыва. Слабые ключи и повторные ID ключей отклоняются. Старые аттестации подписывают роль с разделением доменов и SHA-256 digest объекта (`KOLVRT-MIGRATION-ATTESTATION/3`). Необязательные сессионные аттестации используют `/4` и подписывают роль, digest, время Unix и сессионный challenge. Если внешняя политика доверия задаёт `required_session_id`, она также должна задать `max_attestation_age_seconds`; проверяющий отклоняет другую сессию, просроченную отметку времени или отметку позже `max_clock_skew_seconds` (по умолчанию ноль). Challenge должен поступить проверяющему по независимому каналу. Политики без настроенной свежести продолжают принимать старые аттестации `/3` для совместимости.

Проверяющий сравнивает время с системными часами хоста. Это выявляет просроченные или повторно использованные свидетельства только в пределах настроенной политики и жизненного цикла challenge; это не даёт доверенных часов, постоянного хранилища защиты от повторов, аппаратной аттестации или безопасного управления ключами. Не считайте challenge, сгенерированный самим производителем, независимым подтверждением свежести.

Подписанный манифест пакета связывает байты исполняемого файла и digest спецификаций. Подписанные результаты тестов связывают пакет, спецификацию потребителя/поставщика, набор тестов и контекст. Подписанные результаты бенчмарков связывают оба точных плана, контекст, статистическую политику и digest сырого артефакта. Метаданные runtime и предложения подписываются отдельно. Проверяющий компонент потоково читает и хеширует ссылочные артефакты пакета/спецификации/набора тестов/ядра/нагрузки/протокола/адаптера/сырого результата/снимка. Файлы адресуются именами SHA-256 в нижнем регистре под настроенным хранилищем и ограничены 512 MiB каждый; отсутствующие, подменённые или выходящие за границы артефакты не проходят аутентификацию. Во время проверки хранилище должно быть стабильным снимком с владельцем. Результаты не закрепляют файлы для последующего развёртывания.

Действительная подпись аутентифицирует утверждение настроенного производителя. Она не доказывает, что производитель честно исполнил тесты, собирал данные на указанной физической машине, сохранил независимые выборки или правильно закодировал сырые данные. Производитель должен формировать типизированную сводку из сырых свидетельств и обеспечивать эти обязательства. Проверки свежести с привязкой к сессии реализованы как необязательная политика проверяющего; доверенное время, выдача и учёт challenge, владение ключами, настройка production-подписантов, восстановление после компрометации, защищённый сбор и аппаратная аттестация остаются интеграционной работой. Ручной отзыв во внешней загружаемой политике реализован; онлайн-служба отзыва или доверенная отметка времени не заявлены. Полномочия подписания пакета/манифеста/тестов/бенчмарков отличаются от полномочий развёртывания.

## Запуск и проверка

```text
cargo run --locked -p migration-advisor -- advise crates/migration-advisor/examples/request.json
cargo run --locked -p migration-advisor -- advise request.json --trust-policy trust.json --artifact-root artifacts
cargo test --locked -p migration-advisor
```

[Пример](../../../../crates/migration-advisor/examples/request.json) — каталог модели хоста без живых свидетельств, аттестаций или плана отката. Он сообщает о видимом частичном кандидате с явными пробелами. CLI пишет версионируемый JSON-отчёт в stdout, ошибки в stderr, ограничивает вход запроса и политики доверия 4 MiB и отклоняет неизвестные поля. Схема политики доверия 1 отделена от схемы запроса 3. Digest планов связывают отсортированный JSON плана; подписанные манифесты дополнительно связывают метаданные.

[Тесты планирования/интеграции](../../../../crates/migration-advisor/tests/migration.rs) покрывают альтернативы/циклы/конфликты зависимостей, сохраняемых потребителей, семантические расширения с обеими спецификациями, исчерпание поиска, поддельный результат решателя, неподписанные и частичные свидетельства, шумные прогоны, неопределённые эффекты, бюджеты хвоста, пробелы отката, поведение CLI и сквозную подписанную цепочку. [Криптографические тесты](../../../../crates/migration-advisor/tests/provenance.rs) отклоняют изменённое содержимое/байты, неправильные подписи, роли/ключи и отозванные ключи. Все измерения и ключи производителей в тестах — синтетические данные, включая аутентифицированный пример CLI. Они проверяют механизмы проверки, а не реальное поведение пакетов или ускорение оборудования.

## Оставшаяся интеграция

[Стенд миграции](migration-workbench.md) исполняет контракты процессов хоста, 100 парных прогонов A/B, локальное подписание и изолированный откат неизменяемой нагрузки. Его QEMU exporter связывает kernel-owned process generations, CPU ownership, resident frames и накопленные generic-counter интервалы на границах исключений EL0 с digest фактически загруженного image и поколением маршрутов. Вычисленные наносекунды оценивают время нахождения каждого процесса fixture в EL0; отсчёты охватывают вход и возврат из исключения, поэтому включают накладные расходы границ и не включают native EL1 service time. Они не выделяют стоимость CPU только для адаптера. Этот ограниченный bridge не является live production OS telemetry service: exclusive adapter/native CPU attribution, полное владение installed-state/catalog, реальные контракты приложений и физический ARM64 A/B KOLVRT остаются нереализованными. Миграция установленного пакета KOLVRT или ускорение физического ARM64 не измерены. Исполнитель бенчмарков ждёт двух реальных сопоставимых путей, как требует существующая методология. Production exporter и trusted catalog должны сохранять causal attribution, loss reporting и фактическую consumer/installed-state identity.

Перед production добавьте настройку доверенных производителей и жизненный цикл доверенного времени/challenge, фактическое исполнение контрактов/отката, стабильное сохранение артефактов, проверку зависимости выборок, масштабируемое решение с областями, бюджеты памяти/копирования/энергии и регрессий для конкретных потребителей. Показывайте предложения в пользовательском пространстве; отдельно предоставляйте полномочия на развёртывание с проверками поколения маршрутов, вывода состояния из использования и восстановления. **Совместимость словом не докажешь — контрактом проверишь.** Подписи сохраняют цепочку свидетельств, но не заменяют её исполнение.
