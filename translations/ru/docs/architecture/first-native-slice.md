# Первый собственный сквозной сценарий

Статус: принятая проектная основа EL0 workload, а не завершённая EL0 implementation. Native EL1 kernel и основа двух CPU уже существуют; документ описывает будущую нагрузку изолированных tasks. Сценарий демонстрирует собственную изоляцию и ограниченное взаимодействие: управляющая задача создаёт две изолированные задачи, выдаёт одну конечную точку, передаёт ограниченное сообщение, отзывает приём новых запросов, наблюдает отмену или гибель службы и завершает работу без утечки владения. Это нагрузка проверки правильности, а не заявление о производительности.

## Наблюдаемые критерии приёмки

| Сценарий                                   | Необходимое наблюдение                                                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| Обычный запрос                             | Получатель получает точную копию данных; вызывающий получает один окончательный результат                                 |
| Неавторизованный или устаревший дескриптор | Отказ до приёма в очередь или удержания ресурсов                                                                          |
| Полная очередь или ошибка выделения        | Результат исчерпания ресурсов; нет частичной публикации или потерянного учёта                                             |
| Закрытие во время принятого запроса        | Новый поиск отклоняется; принятый запрос удерживает объект до завершения                                                  |
| Отзыв одновременно с приёмом               | Сериализованный приём либо предшествует отзыву и завершается, либо следует за ним и отклоняется                           |
| Отмена до эффекта                          | Эффекта нет; один результат отмены                                                                                        |
| Отмена после эффекта                       | Завершение или неизвестность эффекта; нет обещания отката или слепого повторения                                          |
| Сбой службы                                | Завершается только эта задача; управляющая задача наблюдает отказ и может запустить новый экземпляр                       |
| Две готовые задачи                         | Каждая получает обслуживание при заявленных предположениях планировщика                                                   |
| Остановка под нагрузкой                    | Прекратить приём, завершить или прекратить запросы, остановить обратные вызовы и прерывания, затем освободить отображения |

## Ограниченная первоначальная конфигурация

Две прикладные задачи и управляющая задача используют отдельные адресные пространства. Конечная точка допускает один незавершённый запрос; сообщение содержит не более 256 байтов данных. Каждая тестовая область имеет два слота дескрипторов. Это небольшие бюджеты теста и первого сценария, выбранные для наблюдаемости исчерпания, а не постоянные максимумы двоичного интерфейса или число законов. Их увеличение требует проверок квот и конкуренции, а не нового архитектурного закона.

Использовать блокировку объекта и явные удерживаемые ссылки до рассмотрения освобождения без блокировок. Поиск дескриптора и получение ссылки происходят под одной блокировкой таблицы объектов. Порядок блокировок: таблица области, объект, очередь; не удерживать их при выделении памяти, внешних вызовах и блокирующих ожиданиях. Обработчик прерывания не получает блокировку, владелец которой может быть им прерван. Прерывание только подтверждает источник и назначает ограниченную отложенную работу.

Начать с одной области планирования и равных долей задач по круговому порядку. Готовая задача обслуживается за один оборот, если прерывания таймера приходят, а невытесняемые участки завершаются в заявленном бюджете. Это условное продвижение, а не гарантия жёсткого реального времени. Зависший процессор или неисправный таймер нарушает предположение и вызывает политику отказа платформы. Фактический квант таймера закрепить при измерении реализации, а не выдумывать целевую задержку сейчас.

## Границы объёма

Для сценария не требуются файловая система, сетевой стек, сохраняемые транзакции, драйвер с DMA, горячее подключение оборудования, чужой двоичный интерфейс, замена кода во время работы или оценка совместимости. Их контракты остаются в архитектуре; реализация активируется только следующей нагрузкой и её приёмочными проверками. Статические образы задач выбирает доверенная управляющая задача; загрузка произвольных программ и доверие пакетам являются отдельной работой.

[Модель угроз](threat-model.md), [кандидат двоичного интерфейса](native-abi.md), [контракт платформы](platform-contract.md) и [аудит законов](law-audit.md) определяют проектную основу. Этап 0 проверяет конечные модели на основной системе и кодирование; этап 1 должен реализовать и проверить настоящее разделение привилегий, сбои, прерывания и таблицы страниц до заявления о работе сценария в KOLVRT.
