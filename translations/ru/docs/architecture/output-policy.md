# Вывод консоли, диагностики и событий

Текст для человека — представление; машинные записи — доказательства. Используются одинаковые проверенные факты, а обычные формулировки не разбираются как ABI ядра. Политика распространяется на новый вывод проекта; текущая реализация охватывает UART ядра и раннер xtask. Измерения совместимости сохраняют отдельный [контракт диагностики](diagnostics.md).

## Консоль для человека

Сохраняется эмблема проекта, затем KOLVRT, профиль исполнения, архитектура и exception level. Формат ASCII: [LEVEL] component: message. Уровни: OK — завершённые проверки, INFO — нейтральный прогресс, WARN — деградация/неполное наблюдение, FAIL — отказ, DEBUG — явно включённые детали. Цвет терминала следует палитре ниже и не несёт единственного значения. Очистка экрана и анимация курсора запрещены; разрешены только SGR-последовательности окраски представления.

Память показывается с единицами и размером страницы; этап наблюдения указан. Обычная загрузка не выводит адреса и JSON. Показываются завершённые этапы и краткий итог. Инициализация, проверка, готовность runtime и выключение различаются. Текущая загрузка проверяет и выключается; работающая постоянная система не заявляется. Число участвовавших CPU не является числом онлайн после выключения. Изолированный тестовый fault не равен отказу ядра.

DEV допускает доверенные диагностические детали. PROD сохраняет защиту и обнаружение отказов, но скрывает адреса исключений и содержимое panic. Не выводятся секреты, credentials, usable handles и пользовательские payloads. Формулировки меняются без версионирования. Новые emitters используют diagnostics::status; сырой log! оставляется для фиксированной эмблемы/заголовка. Сообщения ядра английские; документация переводится на русский.

## Цвета терминала

xtask автоматически окрашивает интерактивный stdout. --color=auto|always|never задаёт режим для команды. Auto отключает цвета при перенаправлении, непустом NO_COLOR или TERM=dumb; явный always имеет приоритет. Окрашиваются метки, затем немедленно сбрасывается стиль. Эмблема остаётся исходной, имя KOLVRT выделяется зелёным. Сырой UART и машинные записи не содержат ANSI; прямой QEMU/debug UART остаётся plain text. Окраска — слой host-представления, а не режим безопасности ядра.

| Метка           | Цвет           | ANSI SGR |
| --------------- | -------------- | -------- |
| OK / NATIVE     | Зелёный        | 32       |
| FAIL / COMPAT   | Красный        | 31       |
| WARN / MIXED    | Жёлтый         | 33       |
| MOSTLY_NATIVE   | Светло-зелёный | 92       |
| LEGACY          | Коричневый     | 38;5;130 |
| INFO            | Голубой        | 36       |
| DEBUG / UNKNOWN | Серый          | 90       |

Палитра состояний сохраняет правила существующего diagnostic contract. Цвет OK означает успешную проверку, а не классификацию NATIVE. Renderer окрашивает только явно опубликованную метку; он не выводит состояние совместимости из текста или нулевого числа вызовов. Метки, scope и доказательства остаются обязательными даже с цветом.

## Машинные события

Build feature machine-events явно включает поток доказательств в любом профиле. Обычные build/debug/run его не включают. cargo xtask test включает его; cargo xtask run --machine включает явно. Один UART несёт текст и записи с завершающим переводом строки:

```text
@KOLVRT/1 {"event":"panic","status":"fail"}
```

Префикс задаёт framing version 1. Каждая запись — один JSON object; в JSON strings нет буквального newline, кавычки/control bytes экранируются. Текущие emitters используют фиксированные имена полей, доверенные постоянные имена тестов, числа и boolean, а не внешнюю интерполяцию строк. Префикс, payload и newline ограничены 4096 байтами. @KOLVRT в начале строки зарезервирован; текст не выдаёт себя за событие. Wall-clock timestamps и общий порядок нескольких CPU не выдумываются.

| Событие     | Обязательный payload и смысл                                                                                   |
| ----------- | -------------------------------------------------------------------------------------------------------------- |
| test        | name, status; уникальный ожидаемый тест, pass или fail                                                         |
| suite       | status, tests; итог после всех ожидаемых тестов                                                                |
| boot        | status, el, timer_irq, active_cpus, secondary_shutdown_verified; итог проверки загрузки, не readiness          |
| el0         | status, processes, workers, faults, switches, reclaimed; счётчики ограниченного упражнения и исход ресурсов    |
| measurement | scope, units, frequency, warmup, iterations, median, p95, p99, samples; наблюдения таймера, не оценка скорости |
| fatal       | status=fail, esr; архитектурный syndrome; адреса остаются в human-диагностике DEV                              |
| panic       | status=fail; детали panic остаются в human-диагностике DEV                                                     |

Status — pass/fail, идентификаторы английские. Неизвестные дополнительные поля могут сохраняться; неизвестные события, неподдерживаемые версии framing, неверные обязательные поля, дубликаты singleton/test, отсутствие итоговой записи и события после успешного итога проваливают проверку. Отказ всегда отменяет прежний успех. Изменение обязательной семантики требует новой версии framing и согласования раннера. Старые записи без framing остаются историческими артефактами, а не live-входом version 1.

xtask сохраняет сырой UART в `target/kernel/*.log`, разобранные payloads — в `*.results.json`. Консоль скрывает framed records и показывает human-итоги; build metadata записываются в `*-build.json` с краткой строкой в консоли. Machine mode означает наличие записей в сыром логе, а не JSON dump в консоли. Human run предназначен для просмотра, а не проверки доказательств; для structured validation используются test или run --machine.

## Ограниченная реализация и контексты исполнения

Polled UART writer не выделяет heap и проверяет длину до вывода. Каждый байт ограничен 1 000 000 опросами TX-full; таймер не предполагается. Слишком длинный вывод, недоступный UART или timeout увеличивают dropped-record counter. Timeout может оставить неполную строку; нет очереди, гарантии retry или скрытого успеха. Отсутствующее/обрезанное доказательство проваливает host validation. При возобновлении вывода итог предупреждает о потерянных записях; невозможность сообщить потерю — явное ограничение.

Пишет только CPU0; IRQ handler не выводит сообщения. CPU1 публикует отказ через существующий SMP path и не становится вторым UART writer. Нет logging locks, рекурсии и panic при отказе writer. Нельзя передавать mutable/side-effectful Display: preflight и вывод форматируют дважды. IRQ, обработчики устройств и recovery должны публиковать ограниченное состояние владельцу, а не добавлять UART calls. Panic маскирует interrupts и пытается вывести запись до выключения. Отказ до публикации UART может быть бесшумным; host обнаруживает timeout/отсутствие результата. Удаление диагностики не удаляет обязательную защиту и корректность (LAW-035).

## Проверка и расширение

Завершающее ревью issue #13 подтверждает закоммиченную реализацию UART/раннера и
сохранённые записи QEMU. Парсер дополнительно отклоняет повторяющиеся ключи JSON на
любом уровне вложенности и зарезервированные маркеры событий внутри частичной человеческой
строки; неоднозначные поля или потерянный перевод строки не должны скрывать свидетельства отказа.
Человеческое представление скрывает каждую строку с зарезервированным маркером. Тесты хоста
заново проверяют реальные сохранённые payloads DEV/PROD для boot, suite и panic;
это не новое выполнение ядра.

Host checks отвергают обрезанный/слишком длинный/неверный framing, неверную версию, отсутствие/дублирование итогов, отсутствие/дублирование тестов и отказ после успеха. Матрица ядра проверяет оба профиля и реальную передачу отказа; human runs проверяют отсутствие event records. Границы preflight — ограничения реализации, а не доказательство времени на silicon. Будущие concurrent logging, внешние строки и транспорты требуют нового аргумента bounded ownership/escaping; политика не вводит logging framework.

Provenance до/после, события DEV/PROD и вывод panic сохранены в [записи проверки вывода](../../../../research/results/output-policy.json). Исходный пример предоставил пользователь; примеры после — реальные QEMU captures.
