# Основа EL0 и планирования

Этап реализует настоящее исполнение AArch64 EL0 и переключение по таймеру на обоих закреплённых CPU. Восемь статически выбранных процессов работают в отдельных адресных пространствах; по четыре закреплены за каждым CPU. Две рабочие задачи завершаются штатно, шесть других вызывают ошибки, не завершая соседние задачи или ядро. Затем загрузочный сценарий освобождает ресурсы и выключает систему. Это ограниченный фундамент, а не работающая ОС общего назначения. Абзац описывает исходную нагрузку фундамента. Последующие этапы добавляют ограниченное копирование пользовательских данных, локальные дескрипторы процессов, передачу, загрузку ELF и ASID с фиксированной привязкой; общий IPC, собственные разрешения доступа, отмена, модели служб и домены безопасности остаются отдельными этапами. Маршрутизация и адаптеры остаются вне зависимостей ядра.

## Исполнение и владение

```text
CPU0: выделить и обнулить кадры → создать закрытые корни → опубликовать неизменяемую настройку задачи
Каждый CPU: получить сигнал запуска → синхронизироваться → получить владение процессом → переключить TTBR0
→ ERET в EL0t → локальный таймер или синхронное исключение → стек и контекст EL1
→ остановить источник/EOI → сохранить задачу → освободить владельца → выбрать готовую задачу → ERET
Нет исполняемых задач: восстановить собственный корень → завершить локальный TLBI → вернуться в EL1
CPU0: получить подтверждения обоих CPU → снять объекты-защитники и учёт → освободить кадры
```

Политика планирования — ограниченный алгоритм выбора по кругу в `crates/kernel-core/src/scheduling.rs`. Привилегированный механизм находится в `crates/kernel/src/scheduler/mod.rs` и `arch/aarch64`. Квант — выбранное планировщиком типизированное значение `Duration` в 1 мс; это не гарантия измеренной задержки. Готовая задача получает ход за один оборот при условии доставки локального таймера и ограниченного времени обработчиков EL1. IRQ не требует выделения памяти, вывода в UART, блокировки очереди или блокировки, прерванной обычным кодом. Шестнадцать квантов и предел нагрузки в две секунды ограничивают враждебные или незавершающиеся образы. По истечении времени незавершённые задачи помечаются как просроченные; исполняемое адресное пространство никогда не освобождается по одному этому основанию.

## Адресные пространства и контекст

Каждый тестовый процесс собственного ядра владеет тремя страницами таблиц, страницей кода, страницей данных и четырьмя страницами стека; необязательные непрозрачные образы добавляют ограниченное число страниц RX. Общие отображения ядра доступны только привилегированному уровню. В общем пользовательском виртуальном адресном пространстве код доступен для чтения и исполнения, но не для привилегированного исполнения; данные и стек доступны для чтения и записи, но не для исполнения. Защитная страница не отображена. Псевдоним адреса процесса существует только в его корне, что позволяет реально проверить отказ при обращении к чужому адресу. Разные метки, записанные по одному виртуальному адресу данных, проверяют, что переключение TTBR выбирает разные физические страницы. Код, данные и устройства ядра недоступны пользователю.

Ограниченный executable loader принимает только ELF64 little-endian AArch64 версии 1, тип ET_EXEC и проверенные заголовки файла размером 64 байта и program header размером 56 байт. Начальный профиль исполнения ядра поддерживает ровно один read/execute PT_LOAD по адресу `0x20040000`, с выравниванием file offset и virtual address на 4 KiB и `p_align`, равным ровно 4 KiB, внутри окна user image 128 KiB. Entry должен находиться в файловых байтах сегмента. Writable, RWX, пересекающиеся, выходящие за окно, переполненные и повреждённые образы отклоняются до резервирования process slot или frames. Страница образа обнуляется до копирования байтов, поэтому BSS и padding начинаются с нуля; instruction cache обслуживается до публикации процесса. ET_DYN, interpreters, PT_DYNAMIC, TLS, relocations, writable data segments и исполнение нескольких сегментов этим начальным адаптером не поддерживаются. Валидный формат сам по себе не разрешает исполнение; создание доступно только bootstrap.

Native root всегда использует ASID zero. Owned process roots получают nonzero leases с учётом ширины из `ID_AA64MMFR0_EL1.ASIDBits` (8 или 16 бит; `TCR_EL1.AS` включает 16-битные tags, если поддерживаются). Lease содержит закреплённый CPU, slot и монотонный software epoch; hardware namespace локален для каждого CPU, поэтому одинаковые номера ASID на CPU0 и CPU1 не конфликтуют. Обычный switch устанавливает TTBR0 с ASID и не инвалидирует TLB. При terminal completion CPU-владелец выполняет `DSB ISH; TLBI ASIDE1; DSB ISH; ISB` до публикации retirement. Detach, local retirement и acquired scheduler completion предшествуют освобождению frames/tables и повторной выдаче tag. Creation rollback освобождает lease сразу только до публикации root.

Fixed affinity остаётся обязательным. Root нельзя запускать на нескольких CPU; будущий shared-root или migration design должен отслеживать residency и ждать подтверждённой remote invalidation до reuse. User roots immutable во время admission, а shared native mapping changes по-прежнему запрещены при user execution. Если кодировка ASID width неизвестна, fallback использует ASID zero и full local flush на каждом switch. `asid-baseline` включает этот режим для сравнения. [Протокол SMP retirement](smp.md) продолжает защищать изменяемые native mappings.

Пользовательский контекст размером 816 байт расширяет кадр GPR/SIMD/FP размером 784 байта регистрами ELR, SPSR, SP_EL0 и TPIDR_EL0. Проверки при компиляции подтверждают смещения и размер в соответствии с ассемблерным кодом. Контекст вызывающей задачи ядра, SP_EL0 и регистр TLS восстанавливаются перед возвратом в EL1. Векторы синхронных исключений и IRQ нижнего уровня используют стек CPU для ядра. Ошибка пользовательской задачи завершает только текущий процесс; ошибка текущего уровня сохраняет фатальную политику ядра. Ожидаемые регистры и метки проверяет доверенный тестовый код, а не механизм проверки полномочий при обработке исключений. Один распознаваемый SVC завершает эту статическую нагрузку; это не стабильный ABI системных вызовов и не операция с полномочиями.

## Проверки и ограничения

Завершение рабочей задачи проверяется после отказов всех трёх парных задач на том же CPU. Это подтверждает возобновление полезной работы после отказов, а не то, что проверяемая задача завершилась раньше них. Итоговая метка измерения — `el0-foundation`; предыдущие записи разработки EL0 остаются историческими.

Исходный фундамент EL0 содержал 53 проверки; актуальные количества DEV/PROD привязаны к исходникам сохранённой матрицы. Проверки ASID доводят пул из четырёх тегов на CPU до исчерпания, затем повторно используют теги с другим физическим содержимым по тому же пользовательскому адресу на обоих CPU. `--asid-reuse-control` пропускает инвалидацию при освобождении и должен провалить `asid_reuse_requires_invalidation`. QEMU TCG сохраняет изоляцию и при пропуске, поэтому отрицательная проверка непосредственно контролирует обязательную инвалидацию. Загрузка без тестового режима также исполняет нагрузку процессов; машинная проверка требует события EL0 до сообщения об успешной загрузке.

Матрица запускает профили DEV и PROD, включая реальное исполнение двух экземпляров минимального ELF в изолированных адресных пространствах EL0, проверку обнуления BSS и заполнения, а также откат повреждённых образов с нарушением W^X, чужими адресами, неверной точкой входа и переполнением диапазона.

Двенадцать контролей распространения отказов должны завершаться ошибкой наряду с контролями отклонения планировщиком в DEV и PROD. `--asid-reuse-control` намеренно пропускает инвалидацию при повторном использовании. [Результаты](../../../../research/results/kernel-el0.json) сохраняют исторический снимок EL0. Парное сравнение в QEMU для задачи #18 сохранено отдельно в [измерениях ASID](../../../../research/results/issue18-asid-measurements.json). [Инвентаризация unsafe-кода](../../../../research/results/kernel-el0-unsafe-audit.json) — перечень для проверки, а не доказательство безопасности.

Сохранённое парное измерение охватывает 32 цикла создания, исполнения и освобождения процесса на каждом CPU с чередованием порядка в восьми парах запусков QEMU; оно фиксирует тики таймера, переключения TTBR, число полных и адресных инвалидаций и повторное использование ASID. Это свидетельство только QEMU TCG. Оно не доказывает поведение слабой модели памяти на оборудовании, аппаратную пропускную способность, жёсткие гарантии реального времени или работу произвольных программ. Подмножество ELF проверяет загрузчик и не означает поддержки приложений общего назначения. Жизненный цикл ASID с фиксированной привязкой и ограниченное безопасное копирование реализованы; доверенная авторизация исполняемых файлов, политика подписантов, динамическая компоновка, записываемые сегменты ELF, миграция, кража задач, вложенные IRQ, отложенное сохранение FPU, подкачка и общий ABI исполняемых файлов требуют отдельных контрактов и проверок. Эти процессы не подтверждают границу DMA, полный собственный сценарий, IPC или домены безопасности.

[ADR-0014](../architecture-decisions/0014-el0-foundation.md) фиксирует размещение, альтернативы и условия пересмотра. Существующие [законы ядра](../architecture/kernel-laws.md), особенно LAW-001, LAW-013, LAW-025, LAW-031 и LAW-041, не меняются: изоляция зависимостей, сохранение учёта занятой памяти, ограниченные требования к платформе и явные пределы продвижения продолжают действовать.

Более поздняя [нагрузка Phase 2](routing.md) использует этот собственный механизм с последовательными пакетами, допускаемыми через CAS, и непрозрачным кодом EL0. Исторические записи EL0 сохраняют контрольные суммы исходников для первоначальных одностраничных образов и одиночного пакета; текущие геометрия и допуск описаны в ADR-0015.

## Обновление ownership Phase 3.0

Более поздний [контракт планировщика](scheduler.md) заменяет описание очереди и подготовки выше: проверки CPU, маски IRQ, фазы и поколения и неблокирующие разрешения контролируют все обращения к хранилищу. Кадр AArch64 и статический проверяющий код разделены. EL0 сам записывает тестовое слово тиков через существующий вызов собственных квантов; IRQ ядра больше не пишет тестовые данные. Хранилище исполнения переживает сессии тестовых образов и полезной нагрузки. Проверки Phase 3.1 добавили жизненный цикл процессов с поколениями, вытеснение в `Registry::step()` и контроли владения планировщиком; см. отчёты процессов и планировщика для точных исходников. Phase 3.2 принимает ограниченный [контракт безопасного копирования пользовательских данных](user-copy.md); IPC и публичные полномочия остаются отдельными этапами Phase 3 — основы собственных процессов и служб.
