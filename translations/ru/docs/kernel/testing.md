# Воспроизводимые проверки ядра

Формат вывода и правила обработки ошибок описаны в [политике вывода](../architecture/output-policy.md). `cargo xtask run` показывает сообщения для человека, `run --prod` запускает профиль PROD, а `run --machine` формирует структурированные свидетельства. `cargo xtask test` включает машинные события в обоих профилях; в обычной консоли JSON скрыт, но остаётся в исходных журналах.

Установите Rust 1.99.0 с rustfmt, clippy и целью `aarch64-unknown-none`, Node.js 18 или новее, а в Windows — 7-Zip. Первая загрузка зависимостей и инструментов требует сети. Сценарий настройки QEMU в Windows распаковывает закреплённый установщик в игнорируемый кэш, проверяет SHA-512 и сохраняет сведения о происхождении; системную службу он не устанавливает. На других системах можно указать QEMU 10.1.0 через `QEMU_AARCH64`. `QEMU_CPU` выбирает другой эмулируемый CPU; по умолчанию используется `cortex-a57`, а `max` проверяет альтернативную конфигурацию ASID. Метаданные запуска сохраняют точный аргумент CPU.

## Команды

```powershell
rustup toolchain install 1.99.0 --profile minimal --component rustfmt --component clippy
rustup target add aarch64-unknown-none --toolchain 1.99.0
./scripts/setup-qemu.ps1
npm ci --ignore-scripts
npm run check
cargo xtask test
```

Матрица xtask собирается с закреплёнными зависимостями, выполняет точный зарегистрированный набор проверок ядра в каждом профиле и отдельно загружает DEV и PROD без тестовых возможностей. Двенадцать контролей распространения отказов, включая пропуск инвалидации при повторном использовании ASID процесса, и контроли отклонения планировщиком должны завершиться с ненулевым кодом и ожидаемыми свидетельствами. Положительная матрица завершается ошибкой, если какой-либо контроль неожиданно проходит. JSON-события должны содержать точный набор проверок и итоговое число тестов. Отсутствие результатов, ошибка эмулятора или превышение 30 секунд завершают команду ошибкой.

В `target/kernel` сохраняются ELF-файлы, SHA-256, отчёты о возможностях и размерах сборки, полная версия и аргументы QEMU, журналы UART, структурированные результаты и инвентаризация `unsafe`. В размер ELF входят отладочные данные; `load_bytes` считает файловые сегменты PT_LOAD, а `memory_bytes` включает обнуляемую память. PROD собирается с оптимизацией release и отладочными данными для изучения; в его загрузочном образе отсутствуют `diagnostics` и `kernel-tests`.

Каждый успешный запуск проверяет исходные измерения и пересчитывает их квантили. Используйте `cargo xtask test --record LABEL`, чтобы сохранить запуск для последующего сравнения; см. [историю измерений](../../../../research/measurements/README.md). `cargo xtask asid-bench` выполняет восемь пар QEMU с чередованием порядка: нагрузка процессов с тегами сравнивается с явным базовым режимом ASID zero и полной инвалидацией; тики таймера, число переключений и инвалидаций TLBI сохраняются в [issue18-asid-measurements.json](../../../../research/results/issue18-asid-measurements.json). Это свидетельства эмулятора, а не аппаратная пропускная способность. Хостовая проверка распределителя сравнивает объём линейного поиска с той же реализацией при отключённом курсоре. Эти проверки не доказывают, что какой-либо алгоритм быстрее во всех случаях.

## Отладка

```text
cargo xtask debug
aarch64-none-elf-gdb target/kernel/dev-boot.elf
(gdb) target remote 127.0.0.1:1234
(gdb) break kernel_main
(gdb) continue
(gdb) info registers
(gdb) bt
```

Установите отдельный GDB с поддержкой AArch64. QEMU останавливается перед входом ядра с помощью `-S` и открывает отладочный сервер только на loopback-интерфейсе. Символы Rust и указатели кадров помогают исследовать исполнение. Для ассемблерных границ исключений нет полной DWARF-размотки стека, поэтому обратная трассировка через исключение не гарантируется.

## Границы свидетельств

Хостовые проверки охватывают безопасные алгоритмы, отклонение повреждённого DTB, кодирование дескрипторов и публикацию данных при конкуренции за блокировку. Проверки в ядре охватывают наблюдаемые аппаратурой ошибки трансляции адресов и IRQ таймера, включая полное восстановление SIMD. Модельные проверки остаются свидетельством проектирования Phase 0. CI повторяет локальные проверки из `.github/workflows/kernel.yml`; наличие настроенного workflow не означает, что CI уже запускался удалённо. См. [разбор отчёта unsafe](unsafe.md) и [границу SMP](smp.md).

## Контроли SMP

Один и тот же протокол проверяется с диагностикой и без неё. Матрица требует 16 именованных проверок SMP и реального вызова `CPU_OFF`, а не только признака `ONLINE`. Дополнительные флаги: `--secondary-panic-control`, `--retirement-control`, `--shootdown-control` и `--remote-tlbi-control`. Каждый контроль должен завершиться ошибкой; положительный запуск проверяет и ненулевой код возврата, и маркер отказа. Образ с пропущенным TLBI должен завершиться ошибкой после того, как CPU1 прочитает отображение. `cargo test --locked` также запрещает обратную зависимость native-ядра от необязательных компонентов. Отдельные проверки пакета Phase 2 запускаются командами `cargo test --locked -p routing --all-features` и `cargo test --locked -p routing --no-default-features`; сами по себе они не подключают маршрутизацию к ядру.

Исторический [фундамент EL0](el0.md) добавил 14 проверок и загрузку без тестового режима. Машинная загрузка требует получить событие EL0 до сообщения об успешном завершении. Его отрицательные контроли — `--user-context-control`, `--user-root-control` и `--user-retirement-control`: они повреждают сохранённый контекст, пропускают переключение корня адресного пространства и пытаются освободить кадры после забытого защитника адресного пространства. Рабочие задачи должны завершаться после отказа соседних задач, подтверждая, что исполнение продолжается.

Запустите `cargo xtask routing test` для отдельной [матрицы Phase 2](routing.md): одновременное исполнение маршрутов native/v1/v2/bug в EL0, минимальные профили PROD, потребители только собственного кода, загрузка без диагностических возможностей и три контроля отказа маршрутизации. Исторический фундамент Phase 2 охватывал 53 проверки ядра и одиннадцать отрицательных контролей; последующие этапы сохраняют отдельные отчёты. Проверки декодирования на хосте не заменяют исполнение в EL0.

## Проверки user-copy Phase 3.2

[Контракт копирования](user-copy.md) добавляет реальные копирования EL0 и изменение данных после создания снимка на обоих CPU, внедрение точного отказа посреди копирования, проверку инициализации выходных данных и отклонение неверных поколений и времени жизни. Записанная матрица Phase 3.2 DEV/PROD требовала 69 именованных проверок и 57 отрицательных контролей, включая перечитывание изменённых данных и отключённое восстановление в обоих профилях. Для каждого CPU сохраняются исходные измерения четырёх ограниченных сценариев размеров и отказа. Та же матрица выполняется без исходных пакетов совместимости; повторяется матрица маршрутизации Phase 2. Проверки на хосте, Clippy и проверки репозитория дополняют свидетельства исполнения в ядре.

## Проверки handles в Phase 3.3

Исходный базовый этап Phase 3.3 [контракта дескрипторов](handles.md) зафиксировал 72 проверки ядра и 67 отрицательных контролей в DEV/PROD; последующие проверки передачи, ELF и ASID имеют отдельные отчёты. Пять внедрённых нарушений проверяют контроль поколения, владельца, типа, небезопасное повторное использование и пропущенную очистку при освобождении. Пять сценариев измерения дескрипторов на каждый CPU дополняют четыре сценария копирования: всего девятнадцать уникальных записей с учётом базового измерения блокировки. После физического удаления пакетов совместимости основная матрица и маршрутизация Phase 2 должны повторно пройти на том же варианте исходников.

## Общая проверка ELF и ASID

[Текущий отчёт объединённого среза](../../../../research/measurements/runs/1791123211326-docs-main-c5c440c-final-fd10fb19115e.json) фиксирует 84 проверки в каждом профиле DEV/PROD, обе загрузки без тестового режима и 70 отрицательных контролей на хосте для `c5c440c`. Он включает ограниченное ожидание/блокировку/пробуждение по собственному событию, безопасное копирование пользовательских данных, передачу дескрипторов с удержанием ресурсов, проверку и откат ELF и освобождение/повторное использование ASID с фиксированной привязкой. [Отдельная регрессия маршрутизации](../../../../research/results/routing-main-c5c440c-regression.json) также прошла для этого среза. Исторические количества выше остаются привязаны к исходным отчётам. Свидетельства охватывают записанные хеши исходников, артефакты, двухпроцессорный QEMU и профили; физическое оборудование, общий IPC, публичные разрешения доступа и постоянные службы в эту проверку не входят.
