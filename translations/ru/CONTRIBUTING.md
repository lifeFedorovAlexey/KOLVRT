# Проверки и форматирование проекта

Использовать стандартные настройки инструментов: rustfmt для Rust, Prettier для Markdown/JSON/YAML, Taplo для TOML, Clippy для диагностики Rust и Markdownlint для структуры документов. Версии закреплены в `rust-toolchain.toml` и `package-lock.json`. Node.js 18 или новее запускает инструменты документов; исследовательские инструменты проекта остаются на Rust. Python не требуется.

Использовать таблицы для коротких сопоставимых значений. Длинные пояснения, границы реализации и пробелы в проверках оформлять разделами или списками, чтобы и отображаемый документ, и его Markdown-исходник оставались читаемыми.

```text
npm ci --ignore-scripts
npm run format
npm run check
```

`format` обрабатывает все поддерживаемые файлы репозитория, включая сгенерированные Markdown. Исключаются загруженные инструменты, зависимости, результаты сборки и генерируемый Cargo файл закрепления зависимостей. У исходных текстовых свидетельств нет форматтера, и переписывать их нельзя. `check` завершается ошибкой при нарушении форматирования, линтинга, тестов, свидетельств моделей или документации. Rust использует стандартный форматтер без особых правил размещения. Prettier сохраняет переносы абзацев; Markdownlint не ограничивает длину строк прозы и таблиц. Повторяющиеся заголовки разрешены в разных разделах.

Настройки рабочей области VS Code включают форматирование при сохранении и рекомендуют соответствующие расширения. TOML обрабатывается Taplo в командах проекта; форматирование при сохранении отключено до установки и выбора совместимого расширения TOML. Другие редакторы могут использовать `.editorconfig` и те же команды. Форматирование и линтинг никогда не утверждают изменённый перевод. Проверить английскую и русскую пары, затем записать каждую изменённую пару через `repository-checks record-translation ru PATH`. После этого отформатировать реестр. Форматирование исследовательской записи может изменить сумму её байтов: перед обновлением суммы двуязычного каталога проверить неизменность значений JSON.

Перед коммитом выполнить `npm run check` и `git diff --check`. Коммиты должны быть тематическими с короткими английскими заголовками. Не включать загруженные инструментарии, каталоги зависимостей, исполняемые файлы и временные копии свидетельств. Тест модели на основной системе не устанавливает правильность ядра. Не подавлять проверку и не перезаписывать свидетельства лишь для сокрытия сбоя.

## Время, аппаратные значения и настройки поведения

Время передаём типом, аппаратные значения называем, настройки поведения отделяем от механики.

Правило относится ко всем магическим числам, для которых тип или имя объясняет единицы измерения, назначение или контракт, а не только ко времени. Использовать типизированные значения и именованные константы там, где они делают код понятнее без дополнительных действий во время исполнения и выделений памяти. Очевидные литералы оставлять на месте: например, инициализацию нулём, единичное приращение или понятный локальный расчёт; не вводить имена лишь ради замены каждого числа.

- **Время:** выражать длительности через `Duration`, например `Duration::from_millis(1)` вместо `1_000_000`. Преобразование в аппаратные тики выполнять на границе с оборудованием.
- **Аппаратные значения:** использовать именованные константы для регистров и битовых масок.
- **Другие значимые значения:** называть размеры буферов, пределы ёмкости, число повторных попыток и коды протокола, если их назначение неясно из локального выражения. Предпочитать константы времени компиляции; не добавлять объекты в куче или инициализацию во время исполнения лишь ради имени значения.
- **Настройки поведения:** квант планировщика, интервалы и таймауты задавать рядом с подсистемой, которая их выбирает. Механика принимает эти настройки, а не выбирает значения поведения самостоятельно.

Желаемый API:

```rust
const TEST_TIMER_DELAY: Duration = Duration::from_millis(1);

cpu::timer(time::deadline_after(TEST_TIMER_DELAY));
```
