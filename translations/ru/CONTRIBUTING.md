# Проверки и форматирование проекта

Для консольных сообщений, диагностики и машинных событий используйте [политику вывода](docs/architecture/output-policy.md). Текст для человека не является машинным ABI.

Использовать стандартные настройки инструментов: rustfmt для Rust, Prettier для Markdown/JSON/YAML, Taplo для TOML, Clippy для диагностики Rust и Markdownlint для структуры документов. Версии закреплены в `rust-toolchain.toml` и `package-lock.json`. Node.js 18 или новее запускает инструменты документов; исследовательские инструменты проекта остаются на Rust. Python не требуется.

Использовать таблицы для коротких сопоставимых значений. Длинные пояснения, границы реализации и пробелы в проверках оформлять разделами или списками, чтобы и отображаемый документ, и его Markdown-исходник оставались читаемыми.

```text
npm ci --ignore-scripts
npm run format
npm run check
```

`format` обрабатывает все поддерживаемые файлы репозитория, включая сгенерированные Markdown. Исключаются загруженные инструменты, зависимости, результаты сборки и генерируемый Cargo файл закрепления зависимостей. У исходных текстовых свидетельств нет форматтера, и переписывать их нельзя. `check` завершается ошибкой при нарушении форматирования, линтинга, тестов, свидетельств моделей или документации. Rust использует стандартный форматтер без особых правил размещения. Prettier сохраняет переносы абзацев; Markdownlint не ограничивает длину строк прозы и таблиц. Повторяющиеся заголовки разрешены в разных разделах.

Настройки рабочей области VS Code включают форматирование при сохранении и рекомендуют соответствующие расширения. TOML обрабатывается Taplo в командах проекта; форматирование при сохранении отключено до установки и выбора совместимого расширения TOML. Другие редакторы могут использовать `.editorconfig` и те же команды. Форматирование и линтинг никогда не утверждают изменённый перевод. Проверить английскую и русскую пары, затем записать каждую изменённую пару через `repository-checks record-translation ru PATH`. После этого отформатировать реестр. Форматирование исследовательской записи может изменить сумму её байтов: перед обновлением суммы двуязычного каталога проверить неизменность значений JSON.

Перед коммитом выполнить `npm run check` и `git diff --check`. Коммиты должны быть тематическими с короткими английскими заголовками. Не включать загруженные инструментарии, каталоги зависимостей, исполняемые файлы и временные копии свидетельств. Тест модели на основной системе не устанавливает правильность ядра. Не подавлять проверку и не перезаписывать свидетельства лишь для сокрытия сбоя.

## Время, аппаратные значения и настройки поведения

Время передаём типом, аппаратные значения называем, настройки поведения отделяем от механики.

Правило относится ко всем магическим числам, для которых тип или имя объясняет единицы измерения, назначение или контракт, а не только ко времени. Использовать типизированные значения и именованные константы там, где они делают код понятнее без дополнительных действий во время исполнения и выделений памяти. Очевидные литералы оставлять на месте: например, инициализацию нулём, единичное приращение или понятный локальный расчёт; не вводить имена лишь ради замены каждого числа.

- **Время:** выражать длительности через `Duration`, например `Duration::from_millis(1)` вместо `1_000_000`. Преобразование в аппаратные тики выполнять на границе с оборудованием.
- **Аппаратные значения:** использовать именованные константы для регистров и битовых масок.
- **Другие значимые значения:** называть размеры буферов, пределы ёмкости, число повторных попыток и коды протокола, если их назначение неясно из локального выражения. Предпочитать константы времени компиляции; не добавлять объекты в куче или инициализацию во время исполнения лишь ради имени значения.
- **Настройки поведения:** квант планировщика, интервалы и таймауты задавать рядом с подсистемой, которая их выбирает. Механика принимает эти настройки, а не выбирает значения поведения самостоятельно.

Желаемый API:

```rust
const TEST_TIMER_DELAY: Duration = Duration::from_millis(1);

cpu::timer(time::deadline_after(TEST_TIMER_DELAY));
```

## Правила реализации

Эти правила применяют существующие архитектурные обязательства к коду; новых законов они не добавляют.

1. Отделять общую логику подсистем от аппаратной реализации. Владение, учёт и политика должны быть независимы от доступа к регистрам и архитектурных инструкций; данные платформы передаются через явные интерфейсы.
2. Публичный безопасный API должен сохранять владение ресурсом. Вызывающий код не должен иметь возможности изменить идентичность выделенного ресурса, освободить чужой ресурс или освободить память, пока отображение удерживает её. Проверки границ и занятости сами по себе не устанавливают владение.
3. Каждый примитив синхронизации должен указывать допустимость использования из обычного кода, обработчиков IRQ и нескольких CPU, а также порядок захвата, допустимую вложенность и границы прогресса. Неподдерживаемые контексты указываются явно; каждый поддерживаемый контекст проверяется до заявления о поддержке.
4. Ограничения тестовой платформы задаются явно в конфигурации платформы. Размер RAM, число активных CPU, размещение устройств и ограничения отображений должны иметь обозначенную область действия; общая логика подсистем не должна неявно принимать предположения тестового стенда.
5. При изменении возможностей обновлять документацию и проверки в том же изменении. Связывать каждый затронутый закон с обеспечивающим его кодом и проверкой, обнаруживающей соответствующее нарушение; явно указывать отсутствующие проверки и границы свидетельств.

### Связи с кодом и проверками

При изменениях на этих границах поддерживать следующие связи и перечень пробелов. Существующие тесты покрывают только указанные случаи. Новые гарантии владения требуют проверок отклонения подмены, освобождения чужого ресурса и освобождения при удерживаемых отображениях; гарантии синхронизации требуют проверок в действительно поддерживаемых контекстах исполнения.

#### LAW-013, LAW-025: владение и учёт

**Граница реализации:** [Physical, Frame и Mapping](../../crates/kernel/src/memory/mod.rs); [Pool](../../crates/kernel-core/src/memory.rs)

**Существующая проверка и оставшийся пробел:** `exhaustion_reuse_and_transactional_rejection` проверяет учёт и отклонение недопустимых диапазонов. `physical_allocator`, `allocation_free`, `physical_exhaustion` и `invalid_mapping_rejection` в [тестах ядра](../../crates/kernel/src/tests.rs) проверяют выделение памяти и поведение отображений. Идентичность Frame закрыта, создание второго физического владельца отклоняется. Контроли xtask ownership и retained-mapping проверяют отклонение второго владельца и отказ освобождать frame после забывания его Mapping guard. Отсутствует: отдельный compile-fail fixture для попытки подмены идентичности через private field; одной занятости pool недостаточно для владения.

#### LAW-041: контексты и прогресс

**Граница реализации:** [Lock и Guard](../../crates/kernel/src/sync/mod.rs); [обработка IRQ](../../crates/kernel/src/interrupt/mod.rs)

**Существующая проверка и оставшийся пробел:** `actual_concurrent_publication_and_exclusion` в [тестах блокировки на основной системе](../../crates/xtask/tests/locking.rs) проверяет настоящую реализацию блокировки с потоками основной системы. Тесты ядра проверяют `locking_exclusion`, `locking_release`, `interrupt_masking` и `irq_simd_context`. Отсутствуют: проверки использования блокировок в IRQ и порядка захвата; потоки основной системы не устанавливают прогресс ядра на нескольких CPU.

#### LAW-031: изоляция платформы и обнаружение

**Граница реализации:** [Проверка платформы](../../crates/kernel/src/platform/mod.rs); [парсер загрузочного описания](../../crates/kernel-core/src/platform.rs); [запуск QEMU](../../crates/xtask/src/main.rs)

**Существующая проверка и оставшийся пробел:** [Тесты загрузочного описания](../../crates/kernel-core/tests/boot_description.rs) отклоняют усечённые и некорректные описания; `physical_discovery` проверяет закреплённую платформу. Runner и ядро используют общую явную конфигурацию платформы в crates/kernel/src/platform/config.rs. Отсутствует: contract test второй платформы, обнаруживающий проникновение предположений в общую логику. Исторический LAW-034 объединён с LAW-001 в [пересмотре законов](docs/architecture/law-review.md); он не является действующим законом об аппаратных ограничениях.

#### LAW-036, LAW-040: утверждения и свидетельства

**Граница реализации:** [Аудит и проверка результатов](../../crates/xtask/src/main.rs); [аудит сценариев](docs/architecture/law-audit.md)

**Существующая проверка и оставшийся пробел:** `cargo xtask test` требует именованные тесты ядра и проверяет передачу ошибок отрицательными контролями; метаданные запуска указывают эмулятор и область активных CPU. `repository-checks check-docs` и `check-translations` обнаруживают нарушенные ссылки, неполные обязательства и устаревшие проверенные пары. Отсутствует: автоматическая проверка соответствия каждого заявления о возможностях свидетельствам поведения; утверждения нужно сверять с сохранёнными результатами.

Проверки на основной системе запускать через `cargo test --locked`, проверки ядра — через `cargo xtask test`, проверки документации — через `cargo run --locked -p repository-checks -- check`. Успех форматтера, инвентаризации исходников или проверки документов не доказывает выполнение этих обязательств поведения.

Phase 1.1 добавляет [multicore checks](docs/kernel/smp.md): двусторонние/повторные IPI, настоящую publication общего lock, задержанное reader acknowledgement, remote translation fault, защищённый retirement/reuse и quiescent CPU_OFF. [Решение](docs/architecture-decisions/0012-multicore-retirement.md) явно ограничивает physical ownership и требует review до добавления writers. Host tests не сертифицируют physical weak-memory behavior.
