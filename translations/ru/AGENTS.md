# Инструкции агентам репозитория

## Архитектура и порядок реализации

Ранняя реализация функциональности поздних этапов допускается. Порядок реализации никогда не определяет архитектуру. Перед построением следующего этапа на раннем коде заново выведите требуемую архитектуру из текущих инвариантов и принятых решений. Переработайте или удалите код, который ограничивает, противоречит или преждевременно закрепляет эту архитектуру. Наличие реализации, затраченные усилия, совместимость с тестами и желание избежать переделки недостаточны для сохранения дизайна.

## Документация и доказательства

Следуйте [политике документации](docs/documentation-policy.md), [правилам истины о feature и impact](docs/knowledge-system.md) и [AI retrieval](docs/ai-retrieval.md) при каждом изменении реализации. До правки найдите текущую canonical feature, законы и принятые ADR. Зарегистрируйте новую функциональность в canonical Markdown feature unit. В том же изменении обновите содержательные изменения scope/status/evidence, полные русские зеркала и затронутые публичные обзоры.

Для изменённых файлов реализации/сборки заполните [декларацию влияния изменения](../../docs/implementation-impact.json) с проверяемым base commit, digests исходников и явными dispositions. Объяснение no-impact требует review человеком; whitespace-touch не подтверждает изменение смысла или evidence. Несовпадение исходников требует STALE либо нового evidence на точных исходниках до VERIFIED. Сохраняйте исторические receipts и append-only переходы feature. Статус реализации, проверка в окружении и готовность разделены.

Запускайте `cargo xtask docs generate`, `cargo xtask docs pilot`, `cargo run --locked -p repository-checks -- record-translation ru PATH` для каждой проверенной изменённой canonical Markdown пары, `cargo xtask docs check-change BASE` и `npm run check`. Используйте реальную базовую ревизию для review. Не заявляйте завершение issue, пока обязательное смысловое или EN/RU review ещё ожидается.

## Изменения карты архитектуры и согласованность уровней

Изменения архитектуры, ответственностей компонентов или их взаимодействий должны обновлять [каноническую карту компонентов ядра](docs/architecture/kernel-component-map.md) и её полный русский перевод в той же задаче и pull request, что и реализация. Фиксируйте конкретные механизмы, прямые взаимодействия, конечные элементы граничных связей и проверенные свидетельства исходного кода; не подменяйте их соседством файлов, транзитивными сокращениями или синтетическими связями. Проверяйте каждый затронутый уровень: входящие и исходящие корневые связи должны продолжаться через соответствующие реальные элементы в подробных представлениях, включая составные ветви и переходы к внешним группам. До обновления хешей исходников проверяйте смысл модели по изменённому коду; незаметное обновление хешей не является review карты.

Для каждого такого изменения запускайте `cargo xtask arena map --check`. Обычная проверка репозитория также вызывает эту обязательную проверку согласованности уровней. Успешные структурные проверки подтверждают идентификаторы, актуальность свидетельств и соответствие корневого и подробных уровней в объявленной модели, но не исчерпывающее смысловое покрытие каждого production-взаимодействия. Проверка не исполняет HTML-просмотрщик; изменения просмотрщика также требуют проверки отображённого результата и взаимодействий. Завершайте смысловую проверку исходников и EN/RU в той же задаче и PR; не переносите отсутствующие обновления карты в последующее issue и не называйте непроверенное покрытие полным.

## Performance и целостность тестов

Нельзя ухудшать runtime performance, ослаблять инварианты или менять production semantics только ради прохождения тестов. Тесты должны проверять требуемую архитектуру. Нельзя добавлять произвольные fixed-duration deadlines публикации или copy-drain в обычную runtime synchronization. Завершение и reclaim требуют фактической acquired quiescence, а не истечения времени. Watchdogs тестов дают диагностику и не заменяют требуемую обработку отказов ядром. Не скрывать failures увеличением таймаутов, retries или выдуманными performance allowances.

## Архитектура: тесты не определяют реализацию

Поведение production-кода должно следовать независимо обоснованным инвариантам и принятым контрактам, а не ожидаемому результату теста. При падении теста нужно установить, есть ли доказанная ошибка реализации или ошибка теста, и исправить именно её. Нельзя добавлять костыли, специальные случаи, синтетические результаты, ослабленные проверки, задержки или ухудшение performance, чтобы тест давал ложноположительный результат. В production-исходниках не должно быть тестового повреждения данных, искусственных rendezvous или fault-injection entry points. Тестовую логику и mutations держать в отдельных test artifacts; положительные тесты проверяют обычную реализацию через её настоящие интерфейсы.

UNIT и INTEGRATION импортируют единственную production-реализацию. E2E собирает настоящий kernel и приложения; сценарий выполняет внешний harness через публичные интерфейсы. Отдельный ELF разрешён только как необходимый внешний ABI/syscall-клиент без production-аналога. Запрещены копии реализации service/supervisor/kernel, изменения копий исходников и любые source-mutating test builds.
